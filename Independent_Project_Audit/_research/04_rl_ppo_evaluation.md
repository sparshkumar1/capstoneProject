## 1. Environment Correctness

File: `rl/env/interview_env.py` (460 lines, read in full).

- **VERIFIED FACT** — Observation space: `spaces.Box(low=0.0, high=1.0, shape=(6,), dtype=np.float32)` (lines 159–161). Action space: `spaces.Discrete(3)` (line 163), with `ACTION_NAMES = {0: "Easier", 1: "Same", 2: "Harder"}` (lines 54–58).
- **VERIFIED FACT** — State vector order, per the module docstring (lines 5–11) and the `reset()`/`step()` construction (lines 309, 409–412): `[perf, avg_perf, confidence, hesitation, progress(t/T), difficulty/5]`. This matches the CLAUDE.md-stated spec.
- **VERIFIED FACT** — `reset()` (lines 297–311): `self.difficulty` is drawn `np_random.uniform(0.3, 0.7)` unless `initial_difficulty` was fixed at construction (used for eval scripts); initial obs is hard-coded `[0.0, 0.0, 0.5, 0.2, 0.0, difficulty]` (line 309) — i.e. performance/avg_perf/hesitation at turn 0 are not sampled from the candidate, they are fixed priors. `super().reset(seed=seed)` is called (line 298), so Gymnasium's own `np_random` seeding path is exercised — this is correct/standard and supports reproducibility **if** the caller passes an explicit seed; `SimulatedCandidate`'s own RNG (`np.random.RandomState(seed)`, `simulated_candidate.py` line 24) is a **separate** RNG stream from the env's `np_random`, so full-run reproducibility requires both the env seed and the candidate's `seed=` kwarg to be fixed together. I found no single call site in `interview_env.py` that automatically forwards the env seed into `sim_candidate`'s RNG — the env takes `simulated_candidate=None` as a pre-constructed object (line 62/165) and never reseeds it from `reset(seed=...)`.
- **INTERPRETATION** — This is a real reproducibility gap in the *class itself*: calling `env.reset(seed=42)` reseeds only the difficulty draw, not the candidate's answer-generation noise. Whether this matters for the frozen Paper 3 results depends on how the training/eval scripts constructed `SimulatedCandidate` instances (see §3) — if they passed a seed explicitly at construction time per training run, the overall run is still reproducible, just not through the Gym `seed=` kwarg alone.
- **VERIFIED FACT** — `step()` (lines 313–459):
  - Pre-action state `prev_obs` is snapshotted (line 316); oracle action computed from it (line 319, calls `oracle_action_from_obs`, lines 192–223).
  - Guardrails applied to the **proposed** action using the pre-action state (line 322, `_apply_guardrails`).
  - Candidate answers at `current_difficulty` (lines 326–329); outputs `performance_score`, `confidence_score`, `hesitation`, `response_time` are read into `perf, conf, hes, t_norm` (lines 330–333).
  - Reward computed (lines 340–398) — see §6.
  - Difficulty is updated **after** reward computation (lines 400–405): Easier → `max(0.1, difficulty-0.1)`; Harder → `min(1.0, difficulty+0.1)`; Same → unchanged. Difficulty is therefore continuous in increments of 0.1, clamped to `[0.1, 1.0]`.
  - New obs built as `[perf, avg_perf, conf, hes, progress, self.difficulty]` (lines 409–412), where `progress = clip(current_step/max_steps, 0, 1)` (line 407).
  - **Termination:** `terminated = self.current_step >= self.max_steps` (line 437); `truncated` is always `False` (returned literal, line 459). There is no early-termination condition (e.g., no "candidate gives up" or divergence cutoff) — every episode runs exactly `max_steps` (default 15) turns.
- **VERIFIED FACT** — CSV logging: every `step()` call appends a row to `log_file` (default `rl/env/training_logs/interview_data.csv`) with the full reward decomposition, guardrail id, oracle match, etc. (lines 416–436). This is a genuinely rich per-step audit trail *when training/eval is run with logging enabled*.
- **OBSERVATION** — `research/experiments/paper3/training/README.md` directory and `research/scripts/run_paper3_study.py` subclass `InterviewEnv` as `AlignedInterviewEnv` (read lines 1–100) to control the semantics of dimension 4 (`aligned_progress`, `aligned_response_time`, `historical_mismatch`, `zero`) — confirming that the *current* `InterviewEnv.step()` natively produces `aligned_progress` (t/T) in `obs[4]`, and that `historical_mismatch` is a deliberately-reconstructed ablation condition, not the live default.

## 2. Guardrails

Files: `rl/guardrails.py` (121 lines, current working-tree version, read in full) and `git diff rl/guardrails.py` against HEAD (commit `b7cad49`, "research: freeze Paper 3 multi-seed RL study and complete audit package").

**What they constrain:** `apply_canonical_guardrails()` takes the pre-action 6-D-equivalent state plus the policy's `proposed_action` and can override it under six deterministic, priority-ordered rules (G0 infra-failure, G4 stuck, G1 overload, G2 anxiety, G5 partial-understanding, G6 strong-performer), returning `(final_action, was_overridden, guardrail_id)`. They are a **post-hoc safety shield**, not a training-time constraint on the policy's action distribution or gradient — the PPO policy is free to propose anything; the guardrail function can silently relabel it.

- **VERIFIED FACT — where they run:** `rl/env/interview_env.py` line 322, `self._apply_guardrails(prev_obs, pre_action)`, called **inside `step()`, every turn** (line 229–245 delegates to `rl.guardrails.apply_canonical_guardrails` when importable). This means guardrails are active **during training** (shaping which action is actually executed and therefore which difficulty/perf trajectory the policy experiences) **and** during inference (`agents/strategy/hybrid_orchestrator.py`, per the guardrails.py module docstring line 6, and confirmed live by `testing_and_evaluation/rl_evaluation/T-N02_ppo_checkpoint_sanity_check.py`, which calls the real `HybridOrchestrator.suggest()`). So guardrails are **both training-time and inference-time**, consistent with what `rl/env/interview_env.py`'s reward computation uses the **post-guardrail** `action` (line 322 reassigns `action` before the reward block at line 341), i.e. **the policy is rewarded/penalized based on the action actually taken after guardrail override, not its raw proposal.** This is an important mechanical detail: it means during training, a guardrail override can turn a `decision_component` mismatch (raw proposal ≠ oracle) into a match (guardrail-corrected action == oracle), silently teaching the policy that whatever the guardrail picked was "correct" for that oracle comparison, functioning as implicit imitation-shaping, not pure open-loop exploration.
- **VERIFIED FACT — the uncommitted diff** (`git diff rl/guardrails.py`): widens rule **G5** ("Partial Understanding") lower bound from `0.40 < perf < 0.65` to `0.30 <= perf < 0.65` (code change at line 109 of the new file vs. line ~95 of HEAD). The diff also adds a dated docstring note ("Fix (2026-11-12, …)") explaining the rationale and explicitly stating the change does not alter G1/G4/G2/G6 or rule priority, and that it is **not retroactively applied** to any already-generated frozen result file.
- **VERIFIED FACT — documented rationale for the diff:** the new docstring (lines 18–30) and the test scripts `testing_and_evaluation/rl_evaluation/T-N02_ppo_checkpoint_sanity_check.py` / `T-N03_guardrail_verification.py` together document the causal chain:
  1. T-N02 (log `testing_and_evaluation/logs/T-N02_output.log`, line 5) ran the real deployed checkpoint (`rl/checkpoints/seed_123/ppo_final.zip`) through `HybridOrchestrator.suggest()` on a constructed boundary scenario `score=0.35, avg=0.35` → the live PPO policy proposed **Harder**.
  2. T-N03 (stale log `testing_and_evaluation/logs/T-N03_output.log`, lines 15–18, labelled "THE_GAP_CASE_from_T-N02") confirmed that, under the *pre-fix* guardrail code, no rule (G1/G2/G4/G5/G6) covered `perf ∈ (0.30, 0.40)`, so a below-average candidate's difficulty could be escalated with **no safety override**.
  3. The current `rl/guardrails.py` working-tree file widens G5 to close exactly this gap, and the current (non-stale) `T-N03_guardrail_verification.py` script (13 cases, read in full) encodes this fix as test case `"THE_GAP_CASE_from_T-N02_NOW_FIXED"` expecting `g5_partial_same`.
- **OBSERVATION — this is a real, documented, test-driven bug fix**, not an unexplained edit: the change is narrow (one boundary, one rule), dated the day before this audit (2026-11-12, audit run 2026-11-13), and is traceable to a specific checkpoint-inference finding. I make no assumption about who/what made the edit or whether it should be committed — that is outside this audit's remit — but the evidence is internally consistent and well-documented.
- **VERIFIED FACT — docstring/code mismatch inside the *current* file (pre-existing, not introduced by this diff):** the module-level rule table (line 13) states `G2 (Anxiety Stabilizer): conf < 0.30 and hes > 0.70 and perf < 0.80 -> Easier if hes > 0.85 else Same`, but the actual G2 implementation (lines 101–102) only ever returns `ACTION_SAME` — there is no `hes > 0.85 → Easier` branch in the code. The docstring describes richer behavior than the function implements. This mismatch pre-dates and is unrelated to the G5 diff; I did not change it.
- **VERIFIED FACT — stale duplicate guardrail logic:** `rl/env/interview_env.py`'s own inline fallback `_apply_guardrails` (lines 229–272, used only if `from rl.guardrails import apply_canonical_guardrails` fails) still hard-codes the **old** G5 boundary `0.40 < perf < 0.65` (line 263) — i.e. it was not updated when `rl/guardrails.py` was patched. In normal operation this fallback path is dead code (the import succeeds), but it is a latent inconsistency: if the import ever broke, the just-fixed gap would silently reappear via this duplicate.
- **VERIFIED FACT — the frozen Paper 3 config does not reflect the fix:** `research/experiments/paper3/frozen_config.yaml` line 52 documents G5 with the **old** boundary `0.40 < perf < 0.65`, consistent with the guardrails.py docstring's own statement that the fix is not applied retroactively to frozen results.

## 3. Training Quality

Files: `rl/training/simulated_candidate.py` (99 lines, read in full), `research/experiments/paper3/frozen_config.yaml`, `research/scripts/run_paper3_study.py` (header read), `research/results/paper3/paper3_training_curves.csv` (481 rows), `paper3_convergence_results.csv`, `rl/checkpoints/seed_123/` (deployed checkpoint directory listing), `research/experiments/paper3/checkpoints/{seed_42,123,456,789,999,historical_mismatch}` (directory listing).

- **VERIFIED FACT — checkpoint artifact count mismatch:** `rl/checkpoints/` (the live/deployed location referenced by `agents/strategy/hybrid_orchestrator.py`) contains **only `seed_123`** (`ppo_final.zip`, `retrain_log.csv`, `vecnormalize.pkl`). The other four seeds' checkpoints exist only under `research/experiments/paper3/checkpoints/{seed_42,seed_456,seed_789,seed_999}/` plus a `historical_mismatch/` variant — i.e., only one of the five trained policies was ever promoted to the deployed/runtime location; the other four exist solely as research/evaluation artifacts.
- **VERIFIED FACT — deployed checkpoint ≠ evaluated checkpoint (different file, same seed number):** `research/CANONICAL_SCIENTIFIC_TRUTH_CURRENT.md` line 79 states the runtime `rl/checkpoints/seed_123/ppo_final.zip` SHA-256 (`2ab8d514ca748abd0ac650d4a0b1676093530b21a16b1586c764b6db8ac54575`) **differs** from the evaluated `research/experiments/paper3/checkpoints/seed_123/ppo_final.zip` SHA-256 (`299437ea0dcdd7a5eed51326e80854bd3bb55341194420b619c5da3d675e24e0`). I did not independently re-hash these files (out of scope for a read-only pass that should avoid touching frozen checkpoints beyond listing), but I take this canonical-truth-file statement as **VERIFIED FACT by citation** since it is the project's own locked current source of truth, explicitly flagged for exactly this kind of discrepancy-tracking purpose.
- **VERIFIED FACT — learning-curve evidence exists and is granular:** `paper3_training_curves.csv` logs, per seed, every 256 steps (`timestep, episode, latest_reward, mean_reward_rolling, action_easier_pct, action_same_pct, action_harder_pct`) across the full 24,576-step run (96 logged points × 5 seeds = 480 data rows + header = 481 lines, matches exactly).
- **OBSERVATION — reward curve is noisy with no strong monotonic trend.** Example (seed 999, rows at t=256 through t=24576): `latest_reward` oscillates between roughly −0.63 and +0.39 throughout the entire run with no visible convergence to a tight band; `mean_reward_rolling` end-of-run values across the 5 seeds are 0.149 (seed42), 0.215 (seed123), 0.219 (seed456), 0.201 (seed789), 0.158 (seed999) — i.e. a fairly narrow band (~0.15–0.22) by the end, but the *trajectory* getting there is not a clean learning curve, it is noisy throughout (consistent with a stochastic simulated-candidate environment and a short, 24.5k-step budget).
- **OBSERVATION — action distribution does shift from near-uniform toward Same-dominant over training**, per `paper3_sensitivity_results.csv`'s companion `paper3_convergence_results.csv` (= same content as the tail of `paper3_training_curves.csv`): at `t=256` all 5 seeds show `action_easier_pct ≈ action_same_pct ≈ action_harder_pct ≈ 0.30–0.37` (near-uniform/near-random); by `t=24576` the 5 seeds converge to roughly `easier≈0.18–0.20, same≈0.49–0.53, harder≈0.28–0.30` — i.e. a real, consistent shift away from uniform-random toward a "Same"-dominant policy, replicated independently across all 5 seeds. This is evidence the PPO optimizer is doing *something* non-trivial and seed-consistent, not pure noise.
- **INTERPRETATION** — 24,576 timesteps (1,638 quarter-minute-scale episodes of 15 steps each) is a small training budget for PPO by general RL standards, though the state/action space here is tiny (6-D box, 3 discrete actions) and the reward is 60% imitation-of-a-hand-coded-oracle (see §6), so a short budget converging to a stable, seed-consistent action-distribution shift is plausible and not inherently suspicious — but it also means the "policy" has limited room to discover anything beyond what the oracle/reward shaping already encodes. The canonical truth doc itself (line 59) states: **"The reward is largely imitation of a rule oracle; the evaluation metric (mean |difficulty − persona target|) is not the training objective."** This directly bears on what "training quality" can mean here: the policy is trained to imitate a hand-written oracle, then evaluated on a different, not-directly-optimized metric.

## 4. Policy Quality

Files: `research/results/paper3/paper3_sensitivity_results.csv` (full file read, 67 rows), `testing_and_evaluation/rl_evaluation/T-N02_ppo_checkpoint_sanity_check.py` + its log, `ablation/results/rl_convergence_summary.md`, `ablation/results/rl_ablation_summary.md` / `sensitivity_summary.md`, `ablation/results/failure_analysis_report.md`, `ablation/results/rl_ablation_missing_input.txt`.

- **VERIFIED FACT — real checkpoint-inference test exists and passes.** `T-N02_ppo_checkpoint_sanity_check.py` loads the actual deployed checkpoint through the actual production wrapper (`HybridOrchestrator`) on 10 constructed scenarios (strong/weak/boundary/nervous-expert/floor/ceiling/declining/improving trend). Log (`T-N02_output.log`) shows `ready=True is_compatible=True`, all 10 scenarios return a valid `Discrete(3)` action and difficulty in `[1,5]`, and the chosen actions are directionally sensible given the constructed inputs (weak→Easier, strong→Same at mid-diff, declining→Easier, improving→Harder, boundary 0.35→Harder [this is exactly the pre-fix gap case], ceiling 0.95 at diff=5→Same). **Source for all of this: `source=ppo`** per the log, i.e. these are genuine raw-PPO-policy decisions, not guardrail/heuristic fallback.
- **VERIFIED FACT — a controlled, single-dimension coordinate sensitivity sweep gives a starkly different picture.** `paper3_sensitivity_results.csv` sweeps each state dimension individually from 0.0 to 1.0 in steps of 0.1, holding the other five dimensions fixed at the neutral point `s0 = [0.5, 0.5, 0.5, 0.5, 0.5, 0.6]` (per `PAPER3_FINAL_REPORT.md` §5), and records the raw policy's chosen action (pre-guardrail, since this is a policy-sensitivity probe, not a live orchestrator call):
  - `s0_perf` swept 0.0→1.0: action is **"Same" at every single value** (rows 2–12).
  - `s2_conf` swept 0.0→1.0: action is **"Same" at every single value** (rows 24–34).
  - `s3_hes` swept 0.0→1.0: action is **"Same" at every single value** (rows 35–45).
  - `s4_progress` swept 0.0→1.0: action is **"Same" at every single value** (rows 46–56).
  - `s1_avg_perf` swept 0.0→1.0: "Easier" only at 0.0–0.1, "Same" for all of 0.2–1.0 (rows 13–23).
  - `s5_diff` swept 0.0→1.0: "Harder" for 0.0–0.5, "Same" for 0.6–1.0 (rows 57–67) — this is the **only** dimension that drives more than one distinct action across its full range.
- **INTERPRETATION — this is a significant finding for policy quality.** Holding all other inputs at a fixed neutral point, the raw trained PPO policy is reported as essentially insensitive to performance (`s0`), confidence (`s2`), hesitation (`s3`), and progress (`s4`) individually — it outputs "Same" regardless of where any one of those four dimensions is set, and only the current-difficulty dimension (`s5`) and, weakly, the historical-average floor (`s1` at its extreme low end) move the action away from "Same." This directly conflicts with the narrative claim in `research/results/paper3/PAPER3_FINAL_REPORT.md` §5 ("Technical Performance (s0, s1): Dominant driver of curriculum adaptation. Scores below 0.40 select Action 0; above 0.70 select Action 2") — the stored sensitivity CSV that report's own §5 is describing does **not** show `s0` crossing any action boundary at all in the univariate sweep. I flag this as a genuine tension between the frozen report's narrative text and the frozen underlying CSV it is nominally summarizing; I do not know (from these artifacts alone) whether the report's text describes a different (joint/multivariate) sweep not included in this CSV, or whether it over-states what the univariate sweep actually shows. Either way, the T-N02 scenario tests (which vary *multiple* fields jointly, e.g. score **and** rolling history **and** difficulty together) do show direction-sensible behavior, while the isolated single-axis sweep does not — suggesting the policy's sensitivity to `perf`/`conf`/`hes` individually may be weak/absent in isolation but becomes visible only in combination with other correlated fields (e.g. the `gap = perf − difficulty` term the oracle/reward uses). This is an **INTERPRETATION**, not a resolved fact.
- **VERIFIED FACT — the project's own canonical-truth audit reaches a related, stronger conclusion independently**, via a different method (counterfactual replay rather than coordinate sweep): `research/CANONICAL_SCIENTIFIC_TRUTH_CURRENT.md` line 77 (`P0-2`, tag `AUDIT-REPLAY`): *"constant-'Same' + the same guardrails gives MAE 0.673, equal to PPO + guardrails (0.673–0.687); 5 of 125 sessions differ. The guardrails account for essentially all of the improvement over Fixed; the heuristic (0.473) is better than every PPO variant. **PPO's contribution under guardrails is not identified by the frozen study. Claim "PPO improves tracking" is withdrawn.**"* This is independent corroboration, from the project's own locked audit document, of the same qualitative signal my sensitivity-CSV read surfaced: once guardrails are active, a trivial constant-action policy performs statistically indistinguishably from the trained PPO policy on the frozen study's own primary metric.
- **VERIFIED FACT — invalid-action handling:** per `T-N02_ppo_checkpoint_sanity_check.py`'s own assertion logic (`ok = action_name in VALID_ACTIONS and 1 <= new_diff <= 5`) and its log output ("All scenarios produced a valid Discrete(3) action and difficulty in [1,5]"), the production wrapper never emits an out-of-range action or difficulty across the 10 tested scenarios. Difficulty clamping (`max(0.1, …)` / `min(1.0, …)` in `interview_env.py` lines 402/404, and the integer `[1,5]` clamp in the orchestrator) prevents genuinely invalid states by construction — this is a clamp, not a learned behavior.
- **OBSERVATION — ablation-pipeline evidence is partially missing / unresolved.** `ablation/results/rl_ablation_missing_input.txt` (dated 2026-04-17) states the RL ablation script (`scripts/ablation_rl.py`) could **not run** because it needs finalized session-report JSON with `action_source`/`ppo_action` fields that were not found anywhere scanned (`orchestrator_logs/`, `apps/backend/orchestrator_logs/`, `data/reports/`, `data/sessions/` — all empty or insufficiently detailed). This is a different, apparently older/separate ablation attempt than the one that produced `rl_ablation_summary.md` (§ below) — the latter's numbers (`0.871 ± 0.064` adaptation ρ etc.) come from a different run that evidently did have the needed input at some point; I could not determine, from these artifacts alone, which run superseded which, or whether `rl_ablation_summary.md`'s numbers and `rl_ablation_missing_input.txt`'s "NOT RUN" status both describe the *current* pipeline or two different historical pipeline versions. **UNKNOWN**: exact provenance/freshness relationship between these two ablation result files.
- **OBSERVATION — `ablation/results/rl_ablation_summary.md` and `sensitivity_summary.md` show suspiciously repeated error bars** across rows describing different experimental conditions: e.g. in `rl_ablation_summary.md`, the rows for "6D+3 actions+guardrails", "5D+3 actions+guardrails" and "6D+5 actions+guardrails" all carry identical PPO-rate uncertainty `± 9.1%`, and `sensitivity_summary.md`'s reward-coefficient sweep carries identical `±0.064 / ±0.0080 / ±0.020 / ±0.068` across three different conditions (lower-weight / baseline / higher-weight). **INTERPRETATION**: identical ± values repeated verbatim across conditions that would be expected to have at least somewhat different sampling variance is consistent with these being a fixed proxy/placeholder uncertainty (e.g. a single bootstrap SD applied uniformly) rather than condition-specific recomputed statistics. I cannot confirm this from the files alone without the generating script; flagged as a quality concern, not a settled fact.
- **VERIFIED FACT — `ablation/results/failure_analysis_report.md`** gives session-level worst-case diagnostics (largest score drop, difficulty jump, worst sessions by final score/regression) for PPO-only, Heuristic-only, and Fixed conditions (10 sessions each) — this is genuine qualitative behavioral evidence (e.g., PPO-only "Largest score drop: −0.4650 ± 0.1203" vs Fixed "−0.2969 ± 0.0546"), though notably **PPO+Guardrails is not included as its own row** in this particular report (only PPO-only, Heuristic-only, Fixed-difficulty) — so this specific artifact does not show the actually-deployed (guardrailed) configuration's failure modes.

## 5. Baseline Comparison

- **VERIFIED FACT — a genuine, matched baseline comparison exists** in `research/results/paper3/PAPER3_FINAL_REPORT.md` §2 ("Baseline Comparison Table, Session-Level Aggregation, N=25 per condition") and the backing CSV `research/results/paper3/paper3_baseline_results.csv`. Conditions compared **under the same 5-persona × 5-evaluation-seed design** (25 sessions each): `Fixed (d=3.0)`, `Heuristic` (threshold-based rule, not PPO), `PPO Raw (Seed 123)`, `PPO+Guardrails (Seed 123)`, `PPO Raw (Historical Mismatch)`, `PPO+Guardrails (Historical Mismatch)`. Metrics matched across all conditions: tracking-error MAE with 95% bootstrap CI, volatility with CI, oscillation rate with CI, overshoot, undershoot, mean final difficulty, mean difficulty changes, guardrail interventions, constraint violations.
- **VERIFIED FACT — numeric results of that comparison** (`paper3_baseline_results.csv`, 6 data rows, all read): Fixed MAE 1.200; Heuristic MAE 0.473; PPO Raw (seed123) MAE 0.804; PPO+Guardrails (seed123) MAE 0.673; PPO Raw (historical mismatch) MAE 0.666; PPO+Guardrails (historical mismatch) MAE 0.640. **The rule-based Heuristic baseline (0.473) has the lowest tracking error of every condition in the table, including both guardrailed PPO variants.**
- **VERIFIED FACT — a second, independent baseline comparison exists** in `ablation/results/rl_convergence_summary.md` and `rl_ablation_summary.md` (10 sessions × 10 or 100 questions), comparing "PPO only", "Heuristic only", and "Fixed difficulty" on final score, final difficulty, score/difficulty smoothness and volatility, and (in `rl_ablation_summary.md`) an "adaptation ρ" (correlation between difficulty and persona skill) metric, where **PPO+Guardrails (ρ=0.871) does outperform Heuristic-only (ρ=−0.040) and PPO-only (ρ=0.467) and Fixed (N/A)** on this particular adaptation-correlation metric — i.e., on this second, different benchmark/metric, PPO+Guardrails looks favorable, in apparent tension with the tracking-MAE comparison above where Heuristic wins.
- **INTERPRETATION — the two baseline comparisons do not agree on which system is "best," and the project's own canonical-truth document resolves the tension explicitly in favor of caution**, not favorable framing: `research/CANONICAL_SCIENTIFIC_TRUTH_CURRENT.md` line 77 states plainly that a trivial constant-"Same" policy combined with the same guardrails reproduces the PPO+Guardrails MAE almost exactly, that guardrails (not the learned PPO policy) account for essentially all of the improvement over Fixed, and that **the claim "PPO improves tracking" is explicitly withdrawn**. ## 6. Reward Quality (Interpretation)

All content in this section is **INTERPRETATION** unless tagged otherwise, built from the exact reward code in `rl/env/interview_env.py` lines 340–398.

- **VERIFIED FACT — reward formula, hybrid mode (default):**
```
reward = hybrid_decision_weight * decision_component      # weight 0.60 (normalized)
        + hybrid_outcome_weight * outcome_component        # weight 0.30
        + hybrid_shaping_weight * shaping_component         # weight 0.10
        + stability_penalty                                  # repeat-easier / zigzag, up to -0.10 each
        + critical_consistency                                # +0.20 match / -1.00 mismatch on 5 "critical" state patterns
        + persona_bias                                         # configurable, default 0.0 for all personas in this file
```
where `decision_component = 1.0 if action == oracle_action else -1.0` and `oracle_action` is produced by the **hand-coded** `oracle_action_from_obs()` (lines 192–223, a 7-rule if/elif ladder on perf/hesitation/confidence/gap).
- **INTERPRETATION — the dominant term (weight 0.60, plus the ±1.0/±0.2 critical-state bonus layered on top) is literally "did you match a hand-written rule oracle," not "did the candidate's measured outcome improve."** The `outcome_component` (weight 0.30) does reward actual performance-delta (`perf - prev_perf`, tanh-clipped), which is the one term tied to a measurable, non-oracle-defined outcome. The `shaping_component` (weight 0.10) is confidence/hesitation/time-based. So, numerically, **up to ~90%** of the hybrid reward's structure (0.60 decision + the critical-state ±0.2/−1.0 bonus, which is itself oracle-derived) is anchored to agreement with a human-written rule set rather than to an independently measured outcome. This is consistent with, and explains, the canonical-truth document's own characterization (line 59): *"The reward is largely imitation of a rule oracle."*
- **INTERPRETATION — does the reward plausibly reflect "sensible difficulty adaptation"?** Partially. The oracle rules themselves (R1–R7, lines 199–223) encode generally sensible interview-pedagogy heuristics (ease off a stuck/weak candidate, don't push a nervous-but-strong candidate, push a clear high-performer). To the extent the oracle is "correct," training the policy to imitate it is a reasonable design choice for a small, cold-start, simulation-only setting with no large labeled dataset of real adaptive-difficulty decisions. The risk is that the policy is then evaluated (tracking MAE against persona targets) on a metric that is **not** what it was trained to optimize (also explicitly noted in the canonical-truth doc, line 59), so a PPO run could score well on reward (matching the oracle) while scoring no better than a trivial baseline on the actual evaluation metric — which is exactly the pattern found in §4/§5 above (constant-"Same"+guardrails ≈ PPO+guardrails on MAE).
- **INTERPRETATION — exploitability.** The `stability_penalty` term (repeat-Easier and zigzag/oscillation penalties, lines 363–367) creates an incentive to settle into "Same" once difficulty stabilizes, independent of whether "Same" is actually the pedagogically correct action in a given state — this is a plausible mechanism (though not something I can prove from logs alone) for why the trained policy's action distribution converges toward Same-dominance (§3 observation) and why the sensitivity sweep (§4) finds "Same" output nearly everywhere except at the difficulty extremes. A policy that simply says "Same" most of the time collects the stability bonus and avoids the −1.0 critical-mismatch penalty whenever the state is not one of the five explicitly-flagged "critical" patterns (which are a minority of the state space), making "mostly-Same" a locally reward-efficient strategy that does not require genuinely reading `perf`/`conf`/`hes`.
- **INTERPRETATION — connection between reward improvement and interpretable behavioral change.** The training-curve data (§3) shows a real, seed-consistent shift in action distribution (uniform-random → Same-dominant) alongside a reward that stabilizes into a noisy but less-negative band. This is an interpretable behavioral change, but it is also exactly the "collapse toward the locally reward-efficient action" pattern described above, not unambiguous evidence of learning *fine-grained, state-conditional* difficulty adaptation — which is the capability the project's narrative (PAPER3_FINAL_REPORT.md §5) claims for `s0`/`s1` but which the sensitivity CSV (§4) does not show in isolation.

## Overall RL Evidence Classification (Interpretation)

**Classification: "limited proof of policy behavior only."**

Justification, synthesizing the above:

1. A genuine Gym-compliant environment with correct 6-D/Discrete(3) spaces, a real post-hoc guardrail safety layer active in both training and inference, and a real, documented, test-driven bug-fix process (the guardrails.py G5 diff) all exist and are evidenced by code and logs — this is **more than a toy stub**; the engineering scaffolding (multi-seed training, matched baseline comparisons, bootstrap CIs, step-level logging, sensitivity sweeps, an internal canonical-truth audit willing to withdraw its own claims) is unusually rigorous for a capstone project.
2. However, on the project's own primary evaluation metric (persona-target tracking MAE), a rule-based Heuristic baseline beats every PPO variant, and the project's own canonical-truth document states that a trivial constant-action policy combined with the same guardrails reproduces the PPO+Guardrails result almost exactly, explicitly withdrawing the claim "PPO improves tracking" (`CANONICAL_SCIENTIFIC_TRUTH_CURRENT.md` line 77).
3. My own independent read of the raw-policy coordinate-sensitivity sweep (`paper3_sensitivity_results.csv`) corroborates this from a different angle: in isolation, the trained policy's output is "Same" across the full range of performance, confidence, hesitation, and progress, moving only in response to current difficulty (and the low extreme of rolling average). This is not the behavior of a policy that has learned fine-grained, state-conditional difficulty adaptation from those signals; it is closer to a policy that has learned to default to a reward-efficient, low-risk action most of the time, with the pedagogically "interesting" adaptivity supplied almost entirely by the deterministic guardrail layer sitting on top of it.
4. The reward function (§6) is structurally ~60–90%-weighted toward imitating a hand-coded oracle rather than toward the metric actually used for evaluation, which is a plausible causal explanation for (2) and (3): the policy may be successfully doing what it was trained to do (agree with the oracle on average, converge to a stable action distribution) without that training objective translating into measurable superiority over simpler baselines on the held-out tracking metric.
5. Multiple seeds (5) were genuinely used with a shared seed set across conditions, satisfying the project's stated methodological bar for seed policy — this is solid procedural evidence, but seed-consistency of a *weak* effect (near-uniform-to-Same-dominant collapse, replicated across 5 seeds) is evidence of **implementation stability**, not evidence of **learned value**.

This body of evidence does **not** support "demonstrates actual RL value" (the project's own audit explicitly withdraws that framing for tracking error, and my own sensitivity-sweep read does not find clear state-conditional adaptivity attributable to the learned policy in isolation). It is also not merely "demonstrates successful implementation only," because there *is* some real, seed-replicated behavioral signal (the uniform→Same-dominant shift, the T-N02 scenario-level directional sensibleness) and a real, if contested, favorable result on a secondary adaptation-correlation metric (`ablation/results/rl_ablation_summary.md`, ρ=0.871) whose relationship to the audited tracking-MAE pipeline is unresolved (**UNKNOWN**, see §5). The evidence sits between those two poles: a working implementation with some genuine, reproducible training dynamics, but with the core causal question — does the *learned PPO policy specifically*, as opposed to the deterministic guardrail layer or a constant-action baseline, do the adaptive work — left open and, where it has been checked (tracking MAE), answered unfavorably by the project's own audit.

**RECOMMENDATION:** Before any manuscript claim of PPO value is drafted, run the same constant-action-plus-guardrails counterfactual against the `ablation/results/rl_ablation_summary.md` adaptation-ρ pipeline that was already run against the tracking-MAE pipeline (§5), and store that replay as a citable artifact rather than a canonical-truth-file sentence, so the "PPO adds value" question is resolved (or remains withdrawn) consistently across both metrics the project currently reports.
