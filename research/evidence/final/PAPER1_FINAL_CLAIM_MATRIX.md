# Paper 1 — final claim matrix (2026-09-20)

**Frame (locked 2026-09-21; wording only, no result changed).** A scoped systems / empirical dependability evaluation of the containment, authority-boundary and failure-handling properties of an LLM-assisted technical-assessment pipeline that can be demonstrated through controlled tests under one specified execution environment (title: "Scoped Evaluation of Containment, Authority Boundaries, and Failure Handling in an LLM-Assisted Technical-Assessment System"). The evidence comprises a controlled containment campaign for the code sandbox, tested failure handling on the repaired build, and a fixed-turn observation of score observables against LLM-authored text. "Failure-aware orchestration" is not the contribution. Every experiment below was designed, written, registered (local annotated tag before execution; repository never pushed) and executed by the same agent (Claude). Two reviews exist: the author's self-audit (`X1_METHOD_AUDIT.md`) and an **independent, read-only Antigravity methodology review of X1-A, X1-B-I and X1-C, completed 2026-09-20, verdict: METHODOLOGICALLY SOUND ONLY AFTER CLAIM NARROWING (no BLOCKER)**. The wording in the last column of every row below is the narrowed wording that review requires (see 'Independent methodology review record'). Build A = `release/app-repair/v1` (`980747ff…`); build B = `sut/X1/build-B` (`beb374f3…`, repairs FLT-03, FLT-06, `llm_status` truthfulness, Qwen token cap). ## Independent methodology review record (Antigravity)

- **What it authorizes:** the narrowed wording in the last column of the table below. - **Approved overall framing:** a scoped systems/dependability evaluation of tested containment, authority-boundary and failure-handling behaviours under a specified harness and environment (restated here in the locked vocabulary: "failure-handling" replaces the earlier "failure-aware"), not a formal-security proof or a universal fault-tolerance demonstration.
- **Provenance of this record:** the review record was supplied to the authoring agent by the project lead (Sparsh) on 2026-09-20. The full Antigravity report is not a repository file available to the authoring session; this document restates only what that record states and reconstructs nothing beyond it. Archive the full report with the submission materials if the venue requires the review to be documented.
- **Review findings on the design:** single-agent design and execution bias, with limited independent perturbation controls; the five repetitions per scenario are deterministic repeatability checks, not random samples, so no inferential statistics or population confidence intervals attach to them; the evidence comes from one environment (Windows 11 + WSL2 + Docker Desktop + local image), so no cross-platform generality is claimed.

## The four HIGH limitations (each must appear in the manuscript)
1. **Numeric sanitization (P1-F5).** NaN, Inf and negative evaluator outputs currently become 0.0 rather than being classified as infrastructure failures. FLT-04 is therefore only a numeric-range sanitization observation, not robust corruption/failure detection.
2. **Follow-up channel (P1-B1, P1-B3).** The X1-B-I test did not test the separate Qwen follow-up generation channel, in which generated follow-up text and target concepts can enter the evaluator's expected-concepts path. Do not claim that all Qwen influence paths are contained or irrelevant to scoring.
3. **ptrace (P1-C2).** SEC-01 containment depended on literal preflight filtering in the tested path; after the filter was bypassed, `ptrace(TRACEME)` returned 0 inside the container. Do not describe the result as intrinsic universal ptrace isolation by Docker.
4. **Qwen timeout (P1-L1).** The shipped Qwen client timeout is 6 seconds, while local CPU generation during the experiment took approximately 19–30 seconds. Latency observations from local generation must not be presented as evidence that the shipped 6-second service path can complete those generations within its configured timeout.

## Other review findings that constrain wording
- FLT-05 tested absence of the Docker CLI, not a Docker daemon being unreachable.
- FLT-08 (WebSocket) and FLT-09 (audio) fault handling were not executed.
- SEC-09: the permissive-control canary reset had a methodological flaw; do not overstate that result.
- Some X1-A timing SLAs were derived from internal SUT constants (a circularity concern). The review record does not say which SLAs are affected, so the timing-based rows below carry the concern in general terms.
- The SEC-08 oracle referenced the SUT constant `ce.DEFAULT_PIDS_LIMIT`; do not present it as an entirely independent external oracle.
