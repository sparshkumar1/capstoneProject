# Claim registry (Phase 0 skeleton)

`CLAIM_REGISTRY.csv` maps every sentence-level number or property that may appear in a manuscript to: the permitted wording, a stored artifact and its SHA-256, the generating script and commit, the configuration, the environment lock, the seeds, and a verification command. **Nothing enters a manuscript without a registry row with status `VALID` (or `VALID` plus a stated scope).** Numbers are inserted into drafts from the registry, never typed by hand.

Created 2026-09-19 (Phase 0). It contains only claims that were checked against stored artifacts in Phase 0 or in the earlier audit, plus the withdrawn statements that must not be revived. It contains **no** manuscript claims from experiments that have not been run (X1/X2/X3). The registry was generated by a one-off documentation script that only hashed and parsed stored files; that script is not a project artifact.

## Columns
| Column | Meaning |
|---|---|
| `claim_id` | Stable ID: `P1-Cnnn`, `P2-Cnnn`, `P3-Cnnn`, `X-Cnnn` (cross-paper). New experiments use `X1A-Cnnn`, `X2C-Cnnn`, … |
| `paper` | 1, 2, 3 or Cross |
| `status` | See below |
| `claim_wording` | The exact permitted (or withdrawn) wording, including scope words |
| `value`, `unit_or_n`, `ci_or_spread` | The number, its unit/denominator and its interval or spread (with method in the wording or notes) |
| `evidence_label` | `FROZEN-VERIFIED`, `CODE`, `AUDIT`, `AUDIT-REPLAY`, `AUDIT-DIAGNOSTIC` (meanings in `CANONICAL_SCIENTIFIC_TRUTH_CURRENT.md`) |
| `artifact_path`, `artifact_sha256` | Stored artifact and its hash at verification time |
| `script_path`, `script_commit`, `config_path` | Generator, the commit that produced the artifact, its configuration |
| `env_lock_sha256` | Hash of the environment lock (`ENVIRONMENT_LOCK_SPEC.md`). Frozen results carry `NOT_RECORDED` |
| `seed_set` | Seeds used |
| `recompute_tier` | T1 hash check · T2 recompute the number from stored per-item data · T3 full re-run reproduction |
| `verify_cmd` | Command or description that checks the claim |
| `superseded_by` | Claim ID(s) that replace it (for `WITHDRAWN` / `HISTORICAL`) |
| `last_verified` | Date, only where verified in the Phase-0 pass |
| `notes` | Scope, caveats, erratum ID |

## Status vocabulary
`VALID` — supported by a stored artifact, wording as stated · `HISTORICAL` — true as a record, not to be used as a current result · `WITHDRAWN` — must not appear in any draft · `EXPLORATORY` — unstored or unregistered diagnostic; not citable · `PENDING-REGISTRATION` — reproduced by replay, awaiting a stored artifact (Phase 1/X3-0) · `NEW-FROZEN` — result of a registered new experiment, after its protocol has run (none yet) · `PLANNED` — reserved ID for a planned claim (none yet).

## Verification structure (claim → artifact → script → hash → environment)
1. **Tier T1** (every row with an artifact): recompute the SHA-256 of `artifact_path` and compare.
2. **Tier T2** (every headline number): recompute the value from stored per-item data with a script and compare within the stated tolerance.
3. **Tier T3** (every new experiment): rerun the experiment from a clean checkout at `script_commit` in the environment with hash `env_lock_sha256` and compare to the stored artifact.
4. **Static rules:** (a) no result-writing script may contain a hard-coded metric literal (the pattern behind `constraint_violations: 0`); (b) a superseded/withdrawn wording list is checked against any file under `paper/`; (c) an environment mismatch is recorded, and a rerun in a different environment is reported as such.
5. A checker (`verify_claims`, planned, **not yet written** — a Phase 1 task requiring approval) will implement T1/T2 and the static rules and exit non-zero on any mismatch. Until it exists, verification is manual and the `verify_cmd` column documents the check.

## Change control
Rows are appended or their status changed only with a dated note in `notes` and user approval. A frozen artifact's hash change is a red flag, not an update.
