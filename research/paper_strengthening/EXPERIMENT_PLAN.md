# Experiment Plan — Proposed, Not Executed

**Status: proposal only.** Nothing in this document has been run. Per this project's standing rule, no new experiment starts without a hashed, git-tagged protocol and an approved run manifest, and no reward/state/action redesign or retraining happens without explicit approval. Each item below states which category it falls into and what approval it needs before any code is written or any run happens.

## Category A — Re-analysis of existing frozen data (no new measurements, lowest risk)

### A1. Hybrid-evaluator ablation write-up
- **RQ:** Does the full 0.15/0.35/0.50 weighting outperform simpler component combinations at tracking human-rated answer quality?
- **Data:** already collected and frozen — `research/results/paper2/paper2_summary_results.csv`, `paper2_ablation_results.csv` (64 constructed answers, 8 questions, 3 raters).
- **Work required:** none beyond what `EVIDENCE_AUDIT.md` §1 already reports. Writing this into the manuscript as a small table + one paragraph is a manuscript task, not an experiment.
- **Approval needed:** none — no new artifact is created beyond citing an existing frozen file.

### A2. Keyword-stuffing dampening check
- **RQ:** Does concept-coverage dampening (Eq. 3) reduce scoring of keyword-heavy, poorly-reasoned answers relative to undampened coverage, on the existing benchmark?
- **Data:** the existing 64-item benchmark already has category labels; if any category is specifically "keyword-heavy without correct reasoning" (per `research/scripts/build_comprehensive_benchmark.py`'s category design), this is a re-analysis: compute S2 vs. S2_effective on the existing stored transcripts and compare against the existing human labels for that category only.
- **Work required:** a short analysis script reading already-frozen inputs; produces no new measurement, no new label, no retraining.
- **Approval needed:** light — confirm with the user that recomputing a *derived statistic* from frozen inputs does not count as "editing a frozen artifact" (it does not touch the frozen files, only reads them), before writing the script.

## Category B — Deterministic code verification (no stochastic result, no new data collection)

### B1. Speaking-rate unit-mismatch, full characterization
- **RQ:** How much does the WPM/words-per-second mismatch (found in this pass, `EVIDENCE_AUDIT.md` §4) change `C_final` and the hesitation score across the realistic range of human speaking rates, and does it affect the RL state or guardrails downstream?
- **Method:** call the existing, unmodified `confidence_scorer.score_breakdown` and `hesitation_scorer.score_hesitation` across a swept range of realistic WPM values (e.g., 80–220 in steps of 10) and realistic words-per-second values (1.5–5.0), holding other inputs fixed at representative values; tabulate the resulting `rate_score`, `hesitation_score`, and `C_final`. This is the same category of check already performed once in this pass (a single deterministic function call), extended to a full sweep table and, ideally, plotted.
- **Data separation / seeds:** not applicable — deterministic, no randomness, no train/test split.
- **Approval needed:** none for the sweep itself (pure function calls on existing code, no modification). Producing a figure from it is a manuscript task.
- **Note:** this does *not* fix the defect. A fix (unit conversion or threshold change) is a system change requiring explicit approval per project rules, and if applied, its effect on downstream RL state/guardrail behavior would need to be re-verified against the same frozen PPO evaluation setup, not silently substituted into it.

## Category C — New experiments requiring a registered, hashed, tagged protocol before execution

### C1. Deterministic follow-up gate — behavioral evaluation
- **RQ:** Does the evidence-gated follow-up trigger (Table V) change LLM output behavior and re-evaluation outcomes relative to (a) no follow-up at all and (b) an always-follow-up baseline?
- **Method (proposed):** construct a fixed, author-labeled set of candidate transcripts spanning each trigger condition (missing mandatory concept, detected misconception, coverage-reasoning gap, partial-answer gap, depth probe) plus boundary cases (scores exactly at each threshold) and adversarial cases (malformed model output, Ollama unavailable, an injected instruction-override attempt in the transcript). Run each case through the real orchestrator + Qwen2.5-7B + evaluator path (not the mock evaluator), record whether the trigger fires as specified, and independently score (by a pre-registered rubric, author-applied, disclosed as such — not claimed as an independent rater) whether the generated follow-up addresses the intended gap.
- **Baselines:** no-follow-up; always-follow-up (fires regardless of evidence).
- **Metrics:** trigger-condition accuracy against the pre-specified expected outcome (this is checkable deterministically since the trigger logic is rule-based); follow-up relevance (author-rubric, disclosed as non-independent); sub-loop termination correctness (bounded at 2 attempts); malformed-output and timeout handling correctness.
- **What's new here relative to X1-B:** X1-B never exercised a live follow-up (the fixed evaluator stub always returned a "strong answer"). This would be the first empirical exercise of that path.
- **Approval needed: full.** This requires live Qwen2.5-7B calls (new data), a written protocol with the exact case set fixed in advance (to prevent post-hoc cherry-picking), a git tag, and an approved run manifest, consistent with every other X1-scale study in this repository.

### C2. PPO reproduction and mechanism probe (expanded design)
- **RQ:** Confirm the existing equivalence finding by an independent replay/retrain check, and determine *why* PPO does not separate from constant-difficulty under guardrails (state signal too weak? reward shaped to imitate the same rule the guardrails enforce? guardrails masking the action space too aggressively?).
- **Baselines (full set, per requested design):** PPO (current checkpoint and, separately, a freshly-retrained-from-seed check); constant-"Same"; the existing threshold heuristic; a fixed schedule (as already in the frozen study, `d=3.0`); and, only if independently justified and clearly labeled as a reference rather than a competitor, an oracle policy with privileged access to the persona's true target difficulty (useful only to bound how much headroom exists above the heuristic — never reported as an achievable baseline).
- **Simulated conditions (expanded beyond the frozen study's 5 personas):** development scenarios spanning improving, deteriorating, fluctuating, and stable performance trajectories, at both short (10-turn) and longer session lengths, with an explicit observation-noise condition (small, disclosed perturbation added to the confidence/hesitation dimensions) to test robustness — all defined and frozen in a development phase, before any held-out confirmatory run.
- **Metrics (expanded):** tracking MAE (as before); volatility (already defined); a new oscillation-count metric (number of action reversals within a session); overshoot/undershoot relative to the persona's target; guardrail-intervention rate reported separately from raw-policy action agreement (as the existing audit already does); performance under the added noise condition specifically.
- **Method:** (i) retrain from the exact frozen config and seeds (`research/experiments/paper3/frozen_config.yaml`) to confirm the stored checkpoints reproduce, on the existing evaluation seeds only, as a pure replication check; (ii) an ablation removing individual guardrail rules one at a time to see which rule(s) drive the equivalence; (iii) an ablation on the reward's decision-alignment term (0.60 weight, described in canonical §D.1 as "largely imitation of a rule oracle") to see whether a differently-shaped reward separates PPO from the oracle it currently imitates — tuned only on new development scenarios, evaluated once on a newly-frozen held-out scenario set never used during (iii)'s tuning.
- **Constraints:** per project rules, this requires explicit approval before any retraining, and any reward/state change must be evaluated on a held-out set frozen *before* the change, with the original held-out evaluation scenarios never used for tuning. If a modified reward or state is found to help, it becomes an isolated research variant (a separate checkpoint/config), never a silent replacement of the frozen, already-published Paper-3 result.
- **Approval needed: full**, and explicitly named in the project's standing rules as requiring sign-off ("do not change reward/state/action definitions or retrain PPO without explicit approval"). The replication check (i) alone, on existing seeds with no reward/state change, is the lowest-risk piece of this item and could be considered for approval independently of (ii)/(iii) if the user wants to sequence it that way.

### C5. System failure-handling and robustness battery
- **RQ:** Does the complete system behave correctly (fail closed, fail visibly, or degrade gracefully rather than silently) when a component is slow, returns an invalid output, is unavailable, or receives noisy/incomplete speech features?
- **Method (proposed):** a fixed, enumerated set of injected-fault scenarios exercised against the real orchestrator with real components wherever feasible (real evaluator, real Qwen where the scenario doesn't specifically require it to be down) and only the specific component under test mocked to fail (e.g., Ollama timeout, malformed JSON from the evaluator, a transcription with zero words, a `NaN`/`None` confidence score, a session resumed mid-follow-up after a simulated crash). Full protocol already complete (`SYNTHETIC_EVALUATOR_BENCHMARK_PROTOCOL.md`). Recommended as the first experiment to seek approval for.
2. **C1 — deterministic follow-up gate, behavioral evaluation.** Still the only way to test the follow-up mechanism specifically, and the one place a genuinely positive finding is plausible. Higher cost (live Qwen calls) and a softer ground truth (author-applied rubric) than D1.
3. **B1 — full speaking-rate sweep and figure.** High value, essentially free, no approval blocker. Should be done regardless of what else is approved.
4. **A2 — dampening/keyword-stuffing category check (existing benchmark).** Now partially superseded by D1's H5, which tests the same question more rigorously at greater scale — worth doing only as a quick cross-check, not as a primary investment.
5. **C5 — system failure-handling battery.** Valuable and directly requested, but should start with a scoping check against existing X1-A coverage before a new protocol is written, to avoid duplicating already-registered work.
6. **C3 — speaking-rate fix + downstream re-verification.** High value once a decision exists on what "corrected" should mean; highest-friction approval since it changes a live scoring path.
7. **C2 — PPO reproduction and mechanism probe.** Highest scientific interest but highest risk of scope creep and of an unintentional "tuned until it worked" narrative; proceed only with a strict, pre-registered held-out split agreed before any reward/state change.
8. **C4 — LLM latency/RAM ablation, reproduced.** Lowest priority; disconnected from the paper's central narrative.

**Kept explicitly separate, per instruction:** the PPO investigation (C2) and the speaking-rate correction study (C3/§6 of `SPEAKING_RATE_PROTOCOL.md`) are independent efforts, use different code paths (RL training vs. audio scoring), and should be registered, approved, and run as two separate protocols, not combined into one.
