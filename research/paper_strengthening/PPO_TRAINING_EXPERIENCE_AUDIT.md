## 2. The `interview_data.csv` file: what it is, and why it cannot be attributed to the frozen checkpoints

- **295,291 data rows**, one header line (matching `InterviewEnv.step()`'s CSV writer in `rl/env/interview_env.py` exactly).
- **No seed column exists in this schema at all** — the logger was never designed to distinguish runs.
- **Row count is ~2.4x the 5 frozen seeds' combined recorded training budget**: `training_meta.json` records 24,576 timesteps per seed → 122,880 combined; this file has 295,291 rows. Since the logger opens the file in append mode and only writes the header the first time the file is created, this is consistent with **many separate invocations accumulated over time** (development/debugging runs, hyperparameter exploration before the final 5 seeds were frozen, or later unrelated local runs) — not a clean record of exactly the 5 kept runs.
- **It is explicitly gitignored** (`training_logs/` in `.gitignore`), meaning the project's own convention treats this as ephemeral local output, never a registered or frozen experimental artifact.
- **What it does confirm, and is treated as confirming, here:** every one of its 295,291 rows has `persona == "normal"` and `skill == 0.6` — **the single training-candidate configuration** that `X3_0B_STATIC_CODE_NOTE.md`'s finding **N1** already established by *static code reading alone* (no execution): `train_ppo_seed` builds the environment with no candidate argument, `SimulatedCandidate`'s defaults are `skill=0.6, persona="normal"`, no code path in the training loop samples a persona, and `retrain_quick.py` (the deployed-checkpoint route) follows the same pattern (N10). This file is fully consistent with, and almost certainly generated by, real executions of that exact training code path — but it cannot be proven to be *the* 5 kept runs specifically.
- **Consequence for how this report uses it:** every number in §3 drawn from this file is labeled **"training-configuration-consistent, not seed-attributable"** — it describes how this exact reward/guardrail/oracle code behaves when actually run with the one candidate configuration training is known (via N1, an independent static-code finding) to have used. It is not claimed to be the literal training trace of `ppo_final.zip` for seed 123 or any other specific seed.
- **A separate, minor, unrelated defect found while reading the schema**: the CSV header names column 9 `time_norm`, but `InterviewEnv.step()`'s writer actually places the `progress` variable (`current_step / max_steps`) there — confirmed by the column's values being exact multiples of `1/15` (`max_steps=15`), not a time-based quantity. Harmless to training itself (the real `progress` variable is used correctly inside `step()`), but worth fixing if this logger is ever relied on again.

## 3. Findings from the training-configuration-consistent log (all counts are exact re-aggregations of the file; "share" figures are of the file's 295,291 rows unless stated otherwise)

### Oracle, PPO-raw, and final action distributions — Harder is **not rare** under the training candidate
| | Easier | Same | Harder |
|---|---|---|---|
| Oracle wants | 40,604 (13.8%) | 199,697 (67.6%) | **54,990 (18.6%)** |
| PPO's raw proposal | 57,630 (19.5%) | 152,322 (51.6%) | **85,339 (28.9%)** |
| Final (post-guardrail) action | 44,601 (15.1%) | 188,664 (63.9%) | **62,026 (21.0%)** |

This is the opposite picture from the P3 evaluation replay, where PPO's raw "Harder" share in guardrail-free states was only 9.8% and it matched the oracle's "Harder" want in **zero** of 120 instances (see the companion report). Under the training-matched candidate, PPO proposes Harder *more* often than the oracle even wants it (28.9% vs. 18.6%).

### Reward signal for "Harder" was frequent, positive, and clearly differentiated — not weak or absent
- Oracle wants Harder in 54,990 rows (18.6% of the file). Of those, the **final action is also Harder in 39,652 (72.1%)**.
- **Mean reward when the oracle wants Harder and the final action is Harder: +0.552** (mean `decision_component` = exactly +1.0, as the reward formula guarantees) — well above the file's overall mean reward of +0.390.
- **Mean reward when the oracle wants Harder but the final action is not Harder: −0.676** — a strongly negative, clearly differentiated penalty.
- Of the 15,338 rows where the oracle wanted Harder but the final action wasn't, **15,335 (99.98%) have `guardrail_id == "none"`** — i.e., essentially none of these misses are guardrail-caused; they are PPO's own raw policy simply not proposing Harder, un-intervened.

**This directly weighs against "insufficient/weak positive reward signal" as the explanation for the evaluation-time blind spot.** Under the one candidate PPO actually trained on, a large, frequent, well-differentiated reward signal for correct "Harder" calls existed and was collected often (39,652 times).

### Guardrail g6 ("push harder") is active and behaves as a corrector, not a blocker
- `g6_strong_harder` fires **13,831 times (4.7% of rows)** — a real, non-trivial rate, in sharp contrast to **zero** activations across all 1,250 turns of the 5-persona P3 evaluation replay (companion report, §3).
- Of g6's 13,831 activations, **8,714 (63%) co-occur with a raw proposal that was already "Harder"** (redundant reconfirmation — the same non-binding pattern `g5` showed in the evaluation replay: 0% override rate there); the remaining **5,117 (37%) actually change the action** (`pre_action != action`), correcting a non-Harder raw proposal to Harder.
- **Checked directly, as required: no guardrail ever blocks or changes away from a correct Harder proposal.** Of the 34,535 rows where the oracle wants Harder *and* PPO's own raw proposal is already Harder, **0 have their final action changed away from Harder** by any guardrail. `forced_action == True` in this log's schema means "a guardrail rule matched," **not** "the guardrail changed the action" (confirmed: `forced_action` and `guardrail_id != "none"` are identical, both 61.29% of rows) — conflating the two would have produced a false impression that guardrails "block" 8,714 correct proposals; they do not block any.
- Guardrail-driven action changes overall: **22.6%** of all rows change action given any guardrail's involvement is possible, **36.8%** of rows where a guardrail actually fired change the action — both notably higher than the P3 evaluation replay's 7.9%/17.6% (companion report, §3). The per-rule pattern also differs: here `g4_stuck_easier` has the *highest* change-rate (74.0%), while at evaluation `g4` had one of the *lowest* (9.0%). This is a further, expected consequence of the two regimes visiting qualitatively different state distributions (one in-distribution candidate vs. five personas, four of them out-of-distribution) — reported as a descriptive contrast, not further interpreted.

## 4. Tracing the mechanism — cause, alternatives, and evidence for each

**The primary, best-supported explanation: training/evaluation persona distribution shift**, already identified by an independent static-code audit (N1) and now given direct quantitative texture:
- PPO trained exclusively on one candidate (`skill=0.6, persona="normal"`) and — under that exact candidate, per §3 — **did** encounter Harder-relevant states often, **did** receive frequent, strongly-differentiated positive reward for resolving them correctly, and **did** learn to propose Harder more than the oracle even asked for.
- At evaluation, only the `normal` persona matches this training distribution; the other four (`struggling_junior`, `overconfident_fail`, `lucky_guesser`, `nervous_expert`) are out-of-distribution for the checkpoint (N1). The companion decomposition report already showed the P3 evaluation's guardrail-free "Harder" opportunity concentrates precisely in `struggling_junior`/`overconfident_fail` — the personas most unlike the training candidate — while `normal` (the one persona that *does* match training) is 100% guardrail-covered at evaluation, giving PPO's (well-trained, in-distribution) Harder behavior no room to even be exercised there.
- This is the most parsimonious account consistent with **both** reports: PPO is not "bad at Harder" in any absolute sense — it is bad at Harder for states unlike the one candidate it ever trained on, and the evaluation study happens to test it almost entirely on such states.

**Alternative explanations considered, and why each is less supported, not merely dismissed:**
1. **Insufficient exposure to Harder-relevant states in absolute terms.** *Not supported*: 54,990 oracle-wants-Harder rows (18.6% of the training-configuration-consistent log) is not a rare event. Ruled out as a primary cause under the training candidate itself — though note this only characterizes the *in-distribution* candidate; it says nothing about exposure to the *other four* personas' states, which is exactly zero by construction (N1), not merely "insufficient."
2. **Missing or weak positive reward signal.** *Not supported*: §3 shows a large, frequent (39,652 instances), and strongly differentiated (+0.552 vs. −0.676) reward contrast specifically for the Harder decision.
3. **The dominant oracle-imitation reward term itself (structural, independent of distribution shift).** *Partially supported, but insufficient alone*: the reward's reliance on oracle-matching is real (confirmed in the companion report) and does make PPO's ceiling depend on how well the oracle's own rule table is learned — but §3 shows PPO *did* learn the Harder direction of that table reasonably well in-distribution (72.1% correct resolution when relevant), so the reward's design is not, by itself, sufficient to explain a *complete* (0-of-120) blind spot at evaluation. It is a contributing structural factor (it is *what* PPO is learning to imitate), not the proximate cause of the specific evaluation-time failure.
4. **Guardrail interactions masking or discouraging Harder during training.** *Not supported*: §3 shows guardrails never block a correct Harder proposal (0 of 34,535), and g6 actively *corrects toward* Harder in over a third of its own activations. Guardrails are not suppressing the Harder signal during training.
5. **State representation or action-space limitation** (e.g., the ±1-level, 3-action design cannot express nuance). *Not directly tested here* — this decomposition does not bear on it either way; it remains a live, untested alternative and is not ruled in or out by this analysis.
6. **PPO optimization/training instability** (e.g., policy collapse, insufficient timesteps). *Not directly tested here* — the coarse `training_curves.csv` action-share trajectories could speak to this with further analysis (not performed in this pass; see §6) but nothing in the fine-grained log suggests instability (reward and action shares in the log are consistent with a policy that converged to sensible in-distribution behavior).

**I have not chosen cause #1 (distribution shift) because it merely agrees with the evaluation result — it is the only explanation directly supported by independent, static-code evidence (N1, established before this pass) *and* now cross-confirmed by execution-level behavior (§3) that itself would have been surprising if distribution shift were false** (a policy that never learned Harder at all, even in-distribution, would have looked identical in the evaluation replay but would show near-zero Harder reward/exposure here too — it does not).

## 5. Recommended targeted improvement — and why "improve Harder" is not automatically "improve MAE"

**Most promising, technically justified change: broaden the training persona distribution before considering any reward or state redesign.** This is a **training-distribution adjustment**, not a reward/state/action redesign, and is the change most directly targeted at the demonstrated mechanism (§4) rather than the merely-plausible structural factor (the oracle-imitation term, §4.3).

- **Why this over a reward change:** the reward already produces the right learning signal *when the relevant states are visited* (§3). Reshaping the reward without changing what states PPO ever sees would not address the demonstrated cause.
- **Why this over a state/action redesign:** nothing in this or the companion report implicates the 6-D state or the 3-action space as insufficient to express the Harder decision — PPO already expresses it correctly in-distribution.
- **Why this over "just use a simpler non-RL policy" (the heuristic):** the frozen P3 result already shows the heuristic beats both PPO and Constant-Same on pooled MAE — this remains true and is not contradicted by anything here. But a heuristic cannot itself be "trained better"; if the paper's interest is specifically in whether *a learned* controller can be made competitive, distribution-broadening is the only lever available that targets a demonstrated (not merely structural) defect. If the paper's interest is only in "what is the best difficulty policy," the heuristic remains the honest current answer regardless of this investigation.

**Do not assume broadening the training distribution would improve MAE.** Three independent reasons this is not guaranteed, stated explicitly per the instruction:
1. **Agreement with the oracle is not the evaluation metric.** Teaching PPO to propose Harder more accurately across personas makes it track the *oracle* better, not necessarily the *target difficulty* better — the oracle is itself an unvalidated, hand-authored heuristic (already noted in the companion report), and the *heuristic* baseline (which is not oracle-shaped at all) currently outperforms PPO on the actual MAE metric.
2. **Persona heterogeneity means a pooled retrain could help some personas and hurt others** — exactly the concern already raised in the companion report's §7 (`normal` has zero guardrail-free room to matter; `struggling_junior`/`overconfident_fail` have the most). Any retrain must be evaluated per-persona, not only pooled.
3. **A different training distribution changes the *entire* learned policy, not just its Harder behavior** — the Easier/Same regions, currently well-calibrated to the single training candidate, could regress in ways this analysis cannot predict.

**Expected benefit, risk, and cost:**
- *Benefit:* a plausible, mechanism-targeted route to closing a demonstrated, specific defect (not a vague "retrain and hope"); if successful, a genuinely improved, defensible RL contribution rather than a null result.
- *Risk:* moderate-to-high — persona-distribution changes are exactly the kind of change CLAUDE.md requires explicit sign-off for (state/training redesign); risk of regressing other personas or destabilizing training is real and must be checked per-persona, not assumed away.
- *Cost:* medium-high — multiple training seeds, a genuine development/confirmatory persona split (below), and materially more compute than the single-candidate training used so far (broadening the distribution likely requires more timesteps for equivalent per-persona coverage).

## 6. Proposed development-only experiment (not run; requires explicit approval before any step)

**Working name:** "E1 — Persona-diverse PPO training, development-only."

- **RQ:** does training PPO against a diverse set of development-only simulated personas (not the 5 frozen evaluation personas) produce a policy whose Harder behavior generalizes better, and does that translate into a lower pooled and per-persona MAE than the frozen PPO+G checkpoints, under the same guardrails?
- **Baselines (identical guardrails throughout):** (a) the existing frozen PPO+G checkpoints (unchanged, as a reference — not retrained); (b) Constant-Same+G; (c) the threshold heuristic; (d) the new persona-diverse PPO+G candidate.
- **Ablation:** persona-diverse PPO **without** the oracle-imitation reward term re-weighted (isolates whether distribution-broadening alone helps) vs. **with** a reward re-weighting that concentrates the decision-component signal on non-guardrail-covered states (tests the two candidate mechanisms from the companion report together).
- **Development personas/seeds:** a **new**, explicitly-labeled set of simulated personas and training seeds, disjoint from the 5 frozen evaluation personas (`normal, struggling_junior, overconfident_fail, lucky_guesser, nervous_expert`) and disjoint from the 5 frozen evaluation seeds (`1001, 2002, 3003, 4004, 5005`) and the 5 frozen training seeds (`42, 123, 456, 789, 999`) — e.g., new skill/behavior-parameter draws spanning the same target-difficulty range (1.0–4.5) but never reused for the eventual confirmatory comparison.
- **Multiple training seeds:** at least 5 new training seeds for the persona-diverse policy, matching the frozen study's own precedent of reporting seed-to-seed variation rather than a single run.
- **Metrics:** pooled MAE; **per-persona** MAE (all 5 frozen evaluation personas, held out from any development/tuning use); the same guardrail-coverage/override/oracle-agreement decomposition as the companion report, applied to the new policy, to check whether the Harder blind spot actually closes; oscillation/volatility, unchanged from the frozen study's existing metrics.
- **Stopping/decision criteria, fixed before any confirmatory run:**
  - **Retain the improvement** only if, on the frozen confirmatory personas/seeds (never used in development), the persona-diverse PPO+G's **pooled** MAE is no worse than Constant-Same+G's, **and** at least one of the two personas with concentrated opportunity (`struggling_junior`, `overconfident_fail`) shows a **per-persona** MAE improvement over both Constant-Same+G and the frozen PPO+G, with the comparison's uncertainty (paired bootstrap, matching the companion report's own methodology) not crossing zero.
  - **Abandon** if pooled MAE regresses relative to Constant-Same+G, if any persona's MAE meaningfully worsens relative to the frozen checkpoint, or if the Harder-blind-spot decomposition shows no material change (i.e., distribution-broadening did not, in fact, change the mechanism it targeted).
  - No result is promoted from development to confirmatory reporting by re-using the same seeds/personas for both, matching the project's standing rule against tuning on confirmatory data.
- **Reproducibility:** a config file (no hard-coded hyperparameters), fixed seeds, git commit recorded with the run, and — this time — the per-step logger fixed to include a `seed` column and to write to a **new, non-gitignored, explicitly-named** output path per run, closing exactly the attribution gap this investigation ran into.
- **This is a Category-C experiment under `EXPERIMENT_PLAN.md`'s own taxonomy**: it changes training data/distribution for PPO, which CLAUDE.md explicitly reserves to explicit user approval before any code runs, and needs a hashed/tagged protocol and an approved run manifest before execution, exactly like the already-named C2 item.

## 7. Minimum additional instrumentation needed (if training evidence is wanted going forward)

Whether or not E1 is approved, the following would close the attribution gap this investigation hit, for any *future* training run (not proposed to run now):
1. Add a `seed` (and ideally a `run_id`/timestamp) column to `InterviewEnv`'s per-step CSV logger.
2. Write each run's log to a fresh, uniquely-named, **non-gitignored** file (or explicitly archive it as a registered artifact) rather than a single shared, append-mode, gitignored path — so a specific checkpoint's exact training experience is always attributable afterward.
3. Fix the `time_norm` header/`progress` value mismatch noted in §2, to prevent a future reader from misinterpreting that column.

None of this is implemented here; it is scoped and named per the instruction to identify minimum instrumentation and stop for approval rather than act on it.

## 8. Summary answers to the final deliverable

- **Exact training evidence and provenance:** no seed-attributable per-step training log exists for the 5 frozen checkpoints; no TensorBoard/W&B records exist anywhere in the repository; the only fine-grained evidence is an untracked, gitignored, non-attributable log confirmed (via its own contents) to reflect the single training-candidate configuration that an independent static-code audit (N1) already established. All findings from it are labeled training-configuration-consistent, not seed-attributable, throughout this report.
- **Does the Harder blind spot have a demonstrated training-time explanation?** **Yes, to the extent evidence allows**: the best-supported explanation is train/evaluation persona distribution shift (N1, static-code-verified) — now shown, via the unattributed-but-consistent log, to be compatible with PPO having learned the Harder direction reasonably well *in-distribution*, with frequent and well-differentiated reward for it, and with guardrails never blocking it. This is not a fully seed-attributed proof, but it is a coherent, cross-checked, multiply-corroborated account, not a single-source hypothesis.
- **Most promising technically justified change:** broaden the training persona distribution (a training-distribution adjustment), not a reward or state/action redesign, evaluated per-persona with a real development/confirmatory split.
- **Expected benefits, risks, cost:** a plausible route to a genuine, defensible RL improvement (benefit); real risk of regressing other personas or destabilizing training, requiring explicit approval (risk); medium-high compute and engineering cost (multiple seeds, new personas, more timesteps).
- **Recommendation on whether PPO retraining is worth the investment:** **worth a scoped, development-only attempt (E1), not a blanket retrain**, given (a) the mechanism is now reasonably well-supported rather than speculative, (b) the heuristic still beats everything on pooled MAE regardless of outcome, so the paper's honest current answer does not depend on E1 succeeding, and (c) the decision criteria in §6 make the attempt cheap to judge and abandon if it doesn't work — this is a bounded, falsifiable bet, not an open-ended research program.

**Nothing executed. No code changed. No retraining. No new data generated. No commit, tag, or push. Stopping here for approval, as instructed.**
