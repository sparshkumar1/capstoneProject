# Fifth research-strengthening pass — independent verification and skeptical review

**Date:** 2026-09-28. **Scope:** this pass was invoked with a very large, 20-phase "comprehensive strengthening" master prompt covering novelty, literature, methodology, statistics, dataset integrity, reliability and manuscript quality for the whole PrepAIred project. Before doing any of that work, this pass first audited what already exists (see §0). The finding: nearly every phase the master prompt asks for has already been executed, to a high and carefully-hedged standard, by prior sessions — three fully self-audited manuscripts (P1, P2-on-hold, P3), a cross-paper originality/overlap/readiness audit, per-paper claim ledgers, reference audits, adversarial reviewer-attack audits, and (for the system paper) an honest research-decision memo that already concludes the paper cannot be written yet. Redoing all of that from scratch would have been wasteful and would have risked contradicting already-verified, carefully-worded claims through hasty re-derivation. Instead, this pass did four bounded, genuinely new things: (1) independently re-derived the P3 primary statistical result from raw data using a fresh implementation, (2) computed one new, previously-flagged-but-undone descriptive statistic from already-stored confirmatory data, (3) root-caused, for the first time across five passes, the one persistent test failure, and (4) ran a fresh skeptical "try to reject this" pass over P1 and P3 (the two papers with a live manuscript) looking specifically for what the existing self-audits might have missed. Nothing was committed, tagged, pushed or submitted. No frozen file, checkpoint, protocol, or confirmatory/held-out data was touched or consumed.

## 1. Independent re-derivation of the P3 primary result (not a re-read of the existing audit — a fresh implementation)

The existing audits (`E1_SERIES_RECONCILIATION_AUDIT.md`, `FINAL_EVIDENCE_AUDIT_AND_READINESS.md`) verified Table I's numbers by reading the stored JSON/CSV outputs. This pass went one step further: it wrote a **new bootstrap implementation from scratch**, without reading `research/confirmatory/X3-A/x3a_analyze.py`, directly against the raw `sessions.csv` (63,000 rows), to check whether the published statistic is genuinely reproducible from the underlying data by an independent method, not merely self-consistent with its own analysis script.

**Result (script: scratchpad, not committed to the repo; reproducible from `research/confirmatory/X3-A/results/sessions.csv` alone):**
- Point estimate: **−0.0350454832** — exact match to the published `x3a_decision.json` value (−0.03504548324999993) to all shown digits.
- Persona-level SD: **0.1015450379** — exact match.
- Cohen's d_z: **−0.3451225582** — exact match.
- 95% two-way cluster bootstrap CI (independent RNG stream, B=10,000, seed 42, personas × training seeds resampled independently): **[−0.0813, +0.0023]**, versus the published **[−0.0818, +0.0021]**. The two intervals differ by about 0.0005 at each bound — the expected order of Monte Carlo variation between two different bootstrap implementations/RNG streams applied to the same 200-cell data matrix, not a discrepancy. **The classification is identical under both: entirely inside ±0.12, upper bound nowhere near the −0.20 superiority threshold.**

**Conclusion:** the deterministic parts of Table I (point estimate, SD, effect size) are exactly and independently reproducible from the raw stored data — they are not an artifact of the project's own analysis code. The stochastic part (the CI) reproduces to within ordinary bootstrap noise under a genuinely independent implementation and does not change the paper's classification. This is stronger evidence than a self-consistency check and closes the strongest form of "did you just trust the script" objection a skeptical reviewer could raise.

## 2. New descriptive statistic: PPO's evaluation-time action distribution on the confirmatory grid

`paper/manuscripts/paper3/reviewer_attack_audit.md` row 9 flags an open item: the manuscript states PPO's *training-time* Same-action share (50.7%–53.5% across seeds) but explicitly says the *evaluation-time* share "was not stored in the publication summary and is therefore not quantified" (Section V-G), and asks whether an author should compute it from `sessions.csv`. `FINAL_EVIDENCE_AUDIT_AND_READINESS.md` (2026-09-28, the most recent audit) repeats that this remains unresolved. This is exactly the kind of read-only, already-stored-data descriptive count Phase F of the master prompt asks for, and it does not touch the confirmatory boundary any differently than the primary analysis already did (same file, same population, no new run).

Computed directly from `research/confirmatory/X3-A/results/sessions.csv`, all 4,000 PPO+G grid sessions (40 personas × 5 training seeds × 20 eval seeds, 40,000 turns):

| Quantity | Value |
|---|---|
| Raw (proposed) action distribution | Same 22,530 (56.3%), Easier 11,102 (27.8%), Harder 6,368 (15.9%) |
| Final (post-guardrail) action distribution | Same 23,717 (59.3%), Easier 13,096 (32.7%), Harder 3,187 (8.0%) |
| Constant-Same+G final distribution (sanity check) | Same 6,871 (85.9%), Easier 1,109 (13.9%), Harder 20 (0.25%) |

**Interpretation, offered for the authors' judgment, not inserted into the manuscript:** PPO's evaluation-time raw Same-share (56.3%) is close to, but meaningfully higher than, its training-time share (50.7%–53.5%) — a real distributional shift between training and evaluation, consistent with the already-disclosed train/eval mismatches in Section III, and worth noting if the authors ever quantify this claim. More importantly for the paper's own argument: **PPO+G's final Same-share (59.3%) is far from Constant-Same+G's (85.9%)** — a 26.6-point gap. This is a useful, concrete number for the "equivalence does not mean identical behaviour" thesis the manuscript already argues qualitatively (via the 50/125 and 25/125 divergence counts on the five-persona replay): even though the two policies are statistically equivalent in tracking MAE on the 40-persona grid, they are proposing/executing a materially different action mix, which is exactly what the paper's discussion already claims but had not shown at grid scale for this specific statistic. Whether to add this to Section V-G is the authors' call (per the reviewer-attack audit's own framing of this as an author decision, not a technical one); the number is reported here so that decision can be made with the evidence in hand.

## 3. Root cause of the persistent test failure (new — not previously diagnosed across four prior passes)

`tests/unit/test_stage11_5_coding_adaptation.py::test_coding_turn_preserves_speech_confidence_and_does_not_fabricate_metrics` has failed identically across all four prior research-improvement passes and again in this one (`obs[4]` obtained `0.0`, expected `0.22`). Every prior pass reported it as "unchanged, pre-existing, unrelated to speech/confidence scoring" without further diagnosis. This pass traced the actual mechanism:

1. The test sets `orch._state["last_time_norm"] = 0.22` directly (bypassing the normal turn-advancement flow), then calls `orch._update_session_state(...)` and finally `build_rl_observation(score=..., current_difficulty=..., session=orch._state)`.
2. `build_rl_observation` (`agents/strategy/hybrid_orchestrator.py:116-139`) computes dimension 4 with this priority: `session["progress"]` first (if present, used as-is, regardless of value) → `session["turn_progress"]` → a `turn_idx/total_turns` computation (only if those keys exist) → **only if none of the above are present**, `session["last_time_norm"]` → a `len(scores)/total_turns` fallback.
3. `InterviewOrchestrator`'s default state initializer sets `self._state["progress"] = 0.0` (`agents/orchestrator/interview_orchestrator.py:255`), and that field is only updated to a real value by `_select_and_send_question`'s question-advancement logic (`interview_orchestrator.py:1684`), a code path the test never calls (it calls `_update_session_state` directly, a lower-level helper used for unit testing individual state transitions).
4. Result: `session["progress"]` is present (`0.0`, not `None`) the whole time, so `build_rl_observation` uses it directly and **never reaches** the `last_time_norm` fallback the test is exercising. Hence `obs[4] == 0.0` regardless of what `last_time_norm` is set to.

This is not a regression, not nondeterminism, and not an evaluator/confidence-scoring bug — the test's other four assertions (confidence, hesitation, `communication_indicators`, `coding_history`) all pass, confirming speech-signal preservation genuinely works. The failure is isolated to dimension 4's definition, and that definition is **already the subject of an explicit, frozen audit**: `research/audit/rl_state_definition.md` §"Dimension $s_4$ — AUDIT FOCUS" documents, as an already-known, already-flagged open research question, that the **training simulator** defines $s_4$ as per-question response latency while the **runtime orchestrator** defines it as session-progress ratio ($t/T$), and explicitly recommends *keeping* this mismatch as a documented covariate-shift limitation for Paper 3 rather than resolving it now, deferring any unification to a future retrained-policy decision ("Priority 3").

The failing test's assertion encodes the *response-latency* semantics — matching a stale module-level docstring at `hybrid_orchestrator.py:17` ("`[4] time_norm`: Normalized response latency") that contradicts the same file's own, more specific and more recently written function docstring 58 lines later (`hybrid_orchestrator.py:75`, "`[4] progress`: Normalized session turn progress ratio (t/T)") and contradicts CLAUDE.md's own compressed state description ("progress t/T"). **The test is stale**: it was written against (or copied from) a superseded intended semantics for this dimension that the current, documented, deliberately-chosen implementation no longer follows at the runtime-orchestrator layer.

This is not fixed in this pass, consistent with CLAUDE.md's standing instruction not to touch this test until the project decides, and because `research/audit/rl_state_definition.md` is a frozen file whose own resolution section explicitly defers the decision. Two safe, mutually exclusive options now exist for the authors, for the first time stated precisely enough to act on:
- **(a)** Update the stale module docstring at `hybrid_orchestrator.py:17` (a one-line, non-behavioral documentation fix) and rewrite the test's expectation to match the documented, current progress-ratio behavior (`obs[4]` should reflect `progress`, not `last_time_norm`, when a real orchestrator session is used) — this requires no behavior change, only correcting stale documentation and a stale test.
- **(b)** Decide that the runtime orchestrator should actually prioritize `last_time_norm` over `progress` for dimension 4 (i.e., change `build_rl_observation`'s priority order) — this is a genuine state-definition change and, per CLAUDE.md, needs explicit approval since it changes RL input semantics.

Neither was executed here. This diagnosis itself is the deliverable: a decision that has been silently deferred for four passes can now actually be made.

## 4. Fresh skeptical review — P1 and P3 (the two manuscripts with live content)

The existing `reviewer_attack_audit.md` files (2026-09-21) are already thorough and largely still valid; this section does not repeat their 16+16 items. It instead asks the master prompt's own Section 17 questions directly, trying genuinely to find what a self-audit — written by the same process that wrote the paper — might be structurally prone to miss.

**1. Strongest argument against novelty (P3).** A skeptical reviewer could argue that "equivalence testing of a guardrailed RL policy against a constant baseline" is methodologically well-trodden (the paper's own §II cites four papers reporting exactly this class of near-null result in adjacent settings [4]–[7]) and that the paper's only genuinely new element is the *guardrail-attribution* framing (isolating what a hand-written safety layer contributes versus the learned policy). That framing is real and is stated as the contribution, but it is a methodological-hygiene contribution, not an empirical discovery — worth being explicit about in any cover letter, since a reviewer expecting a positive RL result will be primed to read this as "yet another negative RL-in-education result" unless the guardrail-isolation design is foregrounded immediately.

**2. Least reproducible central result.** Not the statistics (§1 above shows those reproduce exactly/closely) — the **PPO checkpoints themselves**. The manuscript states plainly (§VIII) that "retraining the checkpoints from the recorded seeds is not reproducible because of unseeded candidate noise." This means the primary evidence base is a fixed, irreproducible artifact: if the five checkpoint files were lost, the confirmatory result could never be regenerated, only re-analyzed. This is disclosed, but a reviewer will treat "cannot be regenerated" as a serious reproducibility weakness regardless of disclosure, and it is worth confirming the checkpoint files themselves (not just `sessions.csv`) are backed up outside the working tree.

**3. Most statistically vulnerable conclusion.** The equivalence margin (±0.12) has, by the manuscript's own repeated admission, "no external empirical justification" and is author-selected. A reviewer competent in equivalence testing (TOST/Lakens, both cited) will immediately ask what result the paper would have reported under a tighter, defensible margin. Using this pass's independently-reproduced numbers: the interval [−0.0818, +0.0021] would still classify as equivalent down to a margin of about ±0.082 (since the lower bound is −0.0818), so the conclusion is not on a knife's edge — but the paper never states this margin-sensitivity number itself, which would be a stronger, self-defending answer to exactly this objection than the current "no justification was found" disclosure alone. This is a genuinely new, cheap, non-invasive strengthening candidate (a single added sentence, traceable to `x3a_decision.json`'s own stored `ci_low` value, no new computation needed) that the existing audits did not surface.

**4. Could a much simpler system achieve the same outcome?** Yes, and the paper already says so more strongly than most authors would: Constant-Same (a single `if` returning "Same") is statistically indistinguishable from the PPO+guardrail system on the primary endpoint. A reviewer's version of this objection is already pre-empted in the manuscript's own words, which is unusual and to the paper's credit.

**5. Is the RL component justified by the evidence?** No claim that it is, and the paper does not claim it is — verified directly against the abstract, §VI and §IX text, all of which explicitly state no superiority and no learner-benefit claim. This is the paper's most carefully-defended property; nothing in this pass's independent checks found a place where the prose overclaims relative to the numbers.

**6. Sufficiency of the P1 evaluation.** P1's containment claims rest on nine author-written attack programs, author-written oracles, and a single-machine environment (Windows 11 + WSL2 + Docker Desktop) — this is explicitly scoped as such throughout, but a reviewer will still ask "why should I believe these nine programs are representative of real attacks." The manuscript's own answer (§VI, "nothing here is a new escape result... it does not measure escape capability against adaptive attackers") is honest but concedes the point rather than answering it; there is no way to strengthen this without a genuinely new, larger adversarial test set, which is out of scope for a documentation pass and not attempted here.

**7. Same-agent evidence (P1).** The reviewer-attack audit already flags this as HIGH risk (row 11: "one AI coding agent designed, ran, repaired and re-tested the campaigns"). This pass agrees this is the single most damaging methodological fact in either paper for a skeptical human reviewer, more damaging than any individual statistic, because it means the defect-finding and defect-fixing and the re-verification that the fix worked were not independent. The manuscript discloses this plainly (§VII) and does not use the word "independent" anywhere near it — that is the right mitigation, but it does not remove the objection, only avoids compounding it with an unearned claim.

**8. Have negative/null findings been preserved?** Checked directly, not assumed: P3's abstract leads with the null result, not a positive framing; Table IV shows PPO's descriptive comparison against the heuristic reverses sign between the two evaluation populations (§V-F, independently verified as correct arithmetic in §1 above's spirit — this pass re-derived $1.0688 - (-0.46414) = 1.53294$, matching the manuscript's stated 1.533); P1's abstract states the two defects and the untested channels as prominently as the passing results. No instance of a negative finding being buried, minimized, or omitted from an abstract was found in either paper.

## 5. What this pass did not do, and why

- Did not re-verify P1's or P3's full reference lists — both already have dedicated, Crossref/arXiv-cross-checked audits (`audit_v2/reference_audit_p{1,3}.md`, 2026-09-21) less than a week old; re-querying the same external sources again would not produce new information and risks flagging transient network differences as findings.
- Did not touch the system paper beyond confirming its blockers file is still accurate (spot-checked: `apps/backend/main.py` is modified in this working tree, but only by prior passes' session-recovery work, not by any difficulty-policy change — the system paper's "no runtime `difficulty_policy` switch exists" finding remains correct). Writing a "contribution audit" or "related-work audit" for a paper with no results section and a research team's own memo already concluding it needs ethics clearance and a human study would manufacture the appearance of progress on a paper that is honestly, correctly blocked. That would violate the master prompt's own integrity rules more than skipping it does.
- Did not attempt the master prompt's literature-review phase (Phase C) as a from-scratch exercise, since P1 and P3 already carry independently source-verified reference lists and bibliographies; redoing a literature search without a specific, named gap to fill would be busywork, not strengthening.
- Did not run the full ~8.5-minute test suite again in this pass beyond the targeted file in §3, since the full suite was run 511.98s ago (relative to the fourth pass, itself very recent) with the one documented failure and no code was changed in this pass that could affect any other test.
