# Chapter 1: Introduction

Technical interviews decide a lot about who gets hired in software engineering, and candidates are judged on more than whether they know the right algorithm or data structure. An interviewer is also watching whether someone can think out loud under pressure, explain a plan clearly, and respond when the question changes direction. Preparation tools have not really kept up with that. LeetCode, HackerRank, and InterviewBit all hand every candidate the same bank of questions at a handful of fixed difficulty levels, and none of them adjusts to how a specific candidate is actually performing. None gives structured feedback on a per-answer basis, and none pays attention to signals that only show up in how someone speaks — hesitation, confidence, how long they take to respond — even though these are clearly part of what a real interview is judging.

A fixed set of questions does not work well for anyone at the extremes: it is too easy for a strong candidate and discouraging for someone still building up the basics. Either way, what comes back is a pass/fail verdict or a single number, not anything that helps them improve. That gap between what a real interview actually involves and what existing preparation tools offer is what this project tries to close, and three things made that newly practical rather than just desirable. Adaptive learning approaches have consistently outperformed fixed-curriculum ones in the broader learning-systems literature. Transformer-based language models, vector similarity search, and open-source reinforcement-learning libraries are now mature enough that a system like this does not need an expensive proprietary API to run on. And per-answer feedback that covers reasoning quality, concept coverage, and specific misconceptions is simply more useful to a learner than one aggregate score — something none of the platforms surveyed in this project's literature review (Chapter 3) currently provide.

PrepAIred is our attempt at addressing these gaps directly. It brings together reinforcement-learning-based difficulty adaptation, a rubric-anchored semantic evaluator, prosodic audio analysis, and LLM-driven hints and feedback, with all of it coordinated by one central orchestrator rather than several agents negotiating with each other. This report describes it that way throughout: a single orchestrator coordinating specialised components, not a multi-agent system with arbitration between agents. The distinction matters here because a separate research-paper draft, supplied alongside this project's materials, describes a second "bounded-authority" coordination layer; checking the codebase directly showed that this layer does not correspond to anything actually implemented (Chapter 10, Section 10.13), so the architecture described in this report matches the real, verified system rather than that draft.

A Proximal Policy Optimisation (PPO) policy chooses between three actions — easier, same, or harder — based on a six-dimensional state vector encoding answer quality, rolling-average performance, audio confidence, hesitation, session progress, and current difficulty. If that choice would be a poor pedagogical call, a guardrail layer of six deterministic rules can override it afterward, and testing in this phase (Chapter 10) found that this guardrail layer, not the learned policy, is actually responsible for most of the system's measurable adaptive behaviour. Answer quality itself is scored by combining Sentence-BERT similarity, FAISS-based concept-coverage scoring, and CrossEncoder reasoning-quality assessment into one rubric-anchored composite score. A locally hosted Qwen2.5 model — confirmed by inspecting the code directly — handles the narrative side of things: feedback content, concept-level correctness and gap analysis (Chapter 6, Table 6.2), contextual hints, and follow-up questions. It plays no role in the numeric score itself, which is always set from a deterministic variable before Qwen is ever called. After every answer, a FeedbackAgent assembles a structured fifteen-field report covering misconception detection, concept-gap identification, and audio-derived communication patterns — a genuine step up from the bare scores that existing platforms hand back.

## 1.1 This Phase's Contribution

Phase-2 of this capstone project (submitted January–May 2026) delivered the implementation described above and documented it across its own eight chapters. Phase-3 does not change that implementation's core architecture, and no model was retrained for this phase. What this phase adds instead is a thorough, evidence-based testing and verification effort, carried out in four stages below. A few of these stages also correct specific places where the Phase-2 report's own account of the system turned out not to match the code, and those corrections are disclosed as they come up:

1. **Inspection.** We went through every architectural and numerical claim in the Phase-2 report line by line against the actual source code, which turned up nine confirmed factual discrepancies (Chapter 10, Section 10.12 has the full detail). A few examples: the evaluator's fallback mechanism was described as a four-module fallback chain, but the code actually implements a single R-gated S2-dampening rule. Question selection was said to use FAISS semantic retrieval, when it is really a deterministic nearest-difficulty-match plus topic-rotation algorithm. The RL action space was reported as five actions; the code enforces `Discrete(3)`, three. The PPO training step count and seed set were also wrong, the evaluator microservice was said to run on FastAPI when it is actually Flask, and the Phase-2 abstract's headline accuracy figure does not trace to any stored artifact — nor does a four-condition ablation study mentioned in the Phase-2 results chapter. Qwen was also credited with a "partial-credit adjustment" to the score, a claim no supporting code path could be found for.
2. **Comprehensive testing.** We built a test strategy spanning 22 categories specific to this project, plus dedicated ML and RL evaluation, and ran it alongside the existing 25-file (21 unit, 4 integration) Python suite and the 28-file frontend suite. Eleven of these test scripts were newly written for this phase and run independently, covering RL-policy inference sanity, guardrail-boundary verification, evaluator API contracts, adversarial and edge-case input handling, database relational integrity, security-configuration review, compatibility, and structured UI inspection.
3. **Diagnosis and justified improvement.** Testing turned up two genuine defects that nobody had caught before: a guardrail-coverage gap that could let difficulty escalate for a below-average-scoring candidate with no safety check in place, and a platform-specific crash in the application launcher on Windows consoles. Both were fixed with small, scoped changes and confirmed through full regression testing to introduce no new failures. A later, separately-scoped extension of this same phase (Section 1.1.1 below) found and fixed four more defects under the same approach.
4. **Results consolidation.** Every number in this report traces back to a stored log, script, or git commit, through a single master results table and a full reproducibility record (git commit, environment, exact rerun commands). Where Phase-2's own figures could not be verified, they have been replaced here with the real, stored figures (Chapter 10).

### 1.1.1 A later extension of this same phase

A later, separately-scoped stage of this same Phase-3 engagement (branch `final-eval/controlled-improvements`) extended the testing programme above in four ways. It made four more narrowly-scoped, regression-verified code fixes. It live-verified that all 18 of the Docker-dependent tests flagged in Chapter 10 (Section 10.9) actually pass once a reachable Docker daemon is available, closing a gap this report had previously only described rather than resolved. It ran an architecture audit that independently confirmed the hub-and-spoke, single-controller classification used throughout this report. And it ran a pre-registered confirmatory statistical test, which found that the PPO policy's own marginal contribution to difficulty-tracking accuracy, beyond the guardrail layer alone, is not statistically distinguishable from zero. The full results of this extension are in Chapter 10, Sections 10.17-10.20, and its findings are folded into the relevant chapters rather than kept separate.

## 1.2 Scope and What Is Not Claimed

This report applies the same evidence discipline throughout: we do not claim results that were not actually measured. No PPO training, retraining, or redefinition of the reward/state/action space happened in this phase — the deployed policy and the project's existing frozen research results are cited as they are, not reproduced or altered. No formal human-subject usability or learning-outcome study was run; that is still future work, as it was in the Phase-2 report. We also do not claim a speech-transcription word-error-rate figure, since there is no verified reference-transcript dataset in this project to measure one against. And the proposed multi-agent "bounded-authority coordination layer" from the separate research-paper draft mentioned above is left out of this report's architecture description entirely, not just in this introduction.

## 1.3 Report Structure

The next two chapters lay the groundwork: Chapter 2 defines the problem and objectives, and Chapter 3 surveys the prior work this project builds on or departs from. Chapter 4 turns that into a concrete requirements specification, after which the design is covered in two passes — Chapter 5 at the high level, Chapter 6 down at the module and interface level — before Chapter 7 walks through how a session actually runs end to end. Chapter 8 then explains the reasoning behind the evaluator, the RL/guardrail combination, and the audio pipeline, with Chapter 9 following up with the implementation decisions and representative pseudocode that realise it. The bulk of the evidence sits in Chapter 10, which covers the full testing and experimentation programme, the discrepancies it turned up, and the later extension to this phase. Chapter 11 pulls that together into verified outcomes, limitations, and what is left for future work, and Chapter 12 closes with the reference list.
