**Reproducibility statement, stated once here and governing this entire chapter:** nothing below is asserted without a trail — every number traces back to either a stored log file or a script under `testing_and_evaluation/` in the project repository that anyone can run independently. All of it came out of the Phase-3 engagement itself, via git commits on `workspace/human-eval-clean-push` and, for Section 10.18–Section 10.19, on `final-eval/controlled-improvements`. ## 10.1 Smoke Testing and the `launch.py` Defect

**Objective:** confirm the full application stack starts correctly. **Procedure:** `python launch.py --backend-only` (evaluator + backend only, the lightest supervised-startup path).

**Result:** both services (evaluator :5000, Flask; backend :8000, FastAPI/uvicorn) started successfully and reached a `ready` state within the launcher's own 45-second readiness check. The backend's own `/health` endpoint confirmed `"pipeline_ready": true`, with the real production evaluator loaded and the real 125-question/125-rubric bank loaded.

**Finding:** `launch.py` itself crashed right after startup, throwing `UnicodeEncodeError`. Tracing it back, the culprit was an unguarded `→` (U+2192) character sitting in a startup-banner `print()` statement, hit on a Windows console still running the default `cp1252` code page. The timing made it worse than a simple crash: the service subprocesses were already spawned by the time the launcher's own process went down, so they just kept running — orphaned, unmonitored, with no clean Ctrl-C path left to shut them down.

**Classification:** genuine implementation bug (platform-encoding-dependent), not an environment/dependency gap.

**Fix applied and verified:** `sys.stdout`/`sys.stderr` reconfigured to UTF-8 with `errors="replace"` at module level, before any `print()` executes. Verification covered four checks. (1) The exact original crash reproduces in isolation under forced `cp1252`. (2) The same print succeeds after the fix, under that same forced condition. (3) `launch.py --help`, which exercises the fix's module-level code, runs cleanly under forced `cp1252`. (4) A full regression-suite rerun shows zero new failures (Section 10.11).

## 10.2 PPO/RL Provenance Verification and Policy Inference Sanity Check

**Objective:** confirm the deployed RL policy's training provenance as documented in the project's existing evidence record, and confirm the deployed checkpoint functions correctly.

**Finding (training-step discrepancy):** the Phase-2 report's claim was that PPO was "trained over 500,000 simulated steps" across seeds (42, 123, 777). That's not what the project's own canonical evidence record shows. What it shows instead is a frozen training run of **24,576 timesteps per seed**, across seeds **{42, 123, 456, 789, 999}** — and the same record separately lists "300,000 PPO steps" as a figure already withdrawn elsewhere for lacking support. Since neither the "500,000" figure nor the (42,123,777) seed set traces to any stored artifact this phase could find, **this report goes with the verified figures and marks the Phase-2 report's version as unverified.**

**Policy inference sanity check (new test, this phase):** loading the real, frozen, deployed checkpoint (`rl/checkpoints/seed_123/ppo_final.zip` + `vecnormalize.pkl`) through the actual production wrapper class and running it against 10 constructed candidate-state scenarios — strong, weak, boundary, nervous-expert, floor, ceiling, declining, improving profiles — produced a valid action (Easier/Same/Harder) every time, with difficulty staying inside [1,5] in all 10 cases. All 10 also traced back to the real PPO policy rather than the heuristic fallback, so the checkpoint is genuinely loading and doing its job. One result did stand out: a score of 0.35 with moderate confidence/hesitation produced a raw "Harder" action for what is, on the face of it, a below-average-scoring candidate — a result Section 10.3 digs into further.

## 10.3 Guardrail Verification and the G5 Coverage Gap

**Objective:** confirm the six documented post-inference guardrail rules fire exactly where their stated conditions specify.

**Procedure:** 11 constructed states, covering each rule's documented trigger boundary plus the Section 10.2 observation, called directly against the real `apply_canonical_guardrails()` function (no mocking).

**Result (before fix):** the 10 originally-documented boundary cases all behaved exactly as expected. What didn't was the Section 10.2 observation (perf=0.35) — testing it directly exposed a real gap. None of the five documented rules reaches performance scores in the interval [0.30, 0.40) once the raw policy is proposing an escalation and confidence/hesitation sit in the moderate range, which meant a below-average-scoring candidate's difficulty could climb with nothing there to stop it.

**Diagnosis:** G4 and G1 only fire below `perf < 0.30`, while G5 (the partial-understanding rule, which holds difficulty at "Same") originally only picked up above `perf > 0.40`. Nothing covered the band in between — a gap in where the boundaries were drawn, not a bug inside either rule individually.

**Fix applied:** G5's lower bound widened from `perf > 0.40` to `perf >= 0.30`, in `rl/guardrails.py`, a single-condition, minimally scoped change. This closes the gap exactly, without altering any other rule's condition, priority order, or returned action.

**Verification:** rerunning the 11-case test plus two new boundary cases gave **13/13 cases passing, zero mismatches**. A full regression-suite rerun (Section 10.11) showed zero new failures.

**Scope note, stated for reproducibility integrity:** this fix only changes what `rl/guardrails.py` does going forward — it can't and doesn't reach back to alter any frozen research result already generated under the old guardrail version. There's a further wrinkle here, confirmed in this phase's later extension (Section 10.19) and then extended again by two more confirmed divergences this report's final correction pass turned up: the live `InterviewOrchestrator` runs its own private guardrail copy (`interview_orchestrator.py::_apply_guardrails`) for actual interview sessions. It's a separate, hand-duplicated version of the same six rules, and it never imports the canonical `rl/guardrails.py` module at all.

Comparing the two directly turns up three confirmed places where they disagree, none of which this report pushes into the live copy. The first is the G5 boundary just described: canonical now reads `0.30 <= perf < 0.65`, while live still carries the original, unfixed `0.40 < perf < 0.65`. The second is the G6 "gap" signal — canonical computes it as `gap = perf - diff_norm` (performance measured against the current question's difficulty), whereas live computes `gap = perf - avg_perf` (performance measured against the candidate's own rolling average), which is a genuinely different quantity, not a cosmetic rename. The third is the G6 `nervous_expert` condition: canonical defines it as a two-part disjunction, `(0.80 < perf < 0.95 AND hes > 0.65) OR (conf < 0.40 AND hes > 0.60)`, but live only implements the second half of that — meaning live never suppresses a G6 escalation for a high-performing-but-hesitant candidate the way the canonical module's own documented rationale (Chapter 6, Section 6.3) says it should. All three stay on the record here as disclosed, unresolved engineering findings rather than being quietly patched as a side effect of writing this report.

## 10.8 Question Selection Correctness and the FAISS-Retrieval Correction

**Finding (architecture discrepancy):** both the diagrams and the prose in the Phase-2 report describe question selection as pulling from a "FAISS VectorStore." That's not borne out by the code. `agents/question_selector/question_selector.py`, checked directly, shows **zero FAISS or embedding dependency** anywhere — just a deterministic nearest-difficulty-match combined with least-recently-asked-topic rotation. Wherever the project's actual FAISS index does live, it belongs entirely to the evaluator (Section 10.4), where it scores concept coverage in answers — not to question selection at all.

**Correctness testing (new, this phase):** a simulated 15-question session was run against the real selector logic. **Result:** all 15 selections were distinct questions. Topic rotation was perfect: no two consecutive turns shared a topic, and all 15 available topics were used exactly once. All 9 tested difficulty-matching queries also returned a value genuinely present in the question bank.

## 10.15 Qwen 2.5 Evaluator Role Verification and the Ninth Discrepancy

A question any evaluation panel would eventually ask is how you verify an evaluator that has a large language model sitting inside it, and this phase went and investigated the actual evaluator/feedback pipeline directly to answer it (full detail in `testing_and_evaluation/Qwen_2.5_Evaluator_Validation_Report.md`). The answer turns out to dissolve the question rather than answer it head-on: Qwen 2.5 never computes, adjusts, or touches the numeric score anywhere in the deployed codebase. `services/evaluator/app.py` doesn't reference Qwen at all, and in `agents/orchestrator/feedback_agent.py` — the one place Qwen is actually called — the final score comes from a deterministic variable set *before* that call and is never reassigned afterward from whatever Qwen returns. What Qwen is confirmed to actually do is generate feedback content (narrative text, and, when reachable, the concept-level correctness/gap/improvement fields in Chapter 6, Table 6.2), produce contextual hints, and generate follow-up questions. A second, independent code-path trace run during this phase's later extension (Section 10.19) re-verified the same finding and additionally confirmed that wherever Qwen's own response schema includes a `final_score` field, it only echoes the evaluator's own number back rather than computing anything of its own.

## 10.16 Discussion

What this chapter's testing programme was actually for was building real confidence, not padding a test count, and a few things come out of it worth sitting with. First, the system's core functional claims hold up under independent re-verification here — they're not just re-asserted from the Phase-2 report, they're substantially real. Second, going code-first rather than taking the prior report at its word surfaced two genuine defects nobody had caught before: a safety-relevant coverage gap and a platform-compatibility crash, both fixed with small, regression-verified changes rather than anything invasive. That same code-first discipline is also what turned up nine discrepancies between the Phase-2 report's prose and what the implementation actually does, and this report corrects each of them with evidence behind it rather than just asserting a different number. The Qwen investigation in Section 10.15 is worth generalising from, too: the component drawing the most scrutiny — an embedded LLM, in this case — isn't necessarily where the real verification burden actually sits. Two things stayed genuinely open at the end of the original testing pass rather than resolved: Docker-daemon-dependent test coverage, which did get closed later (Section 10.18), and the pre-existing known test failure, which stays explicitly deferred, consistent with this project's policy against quietly patching something once it's been flagged.

## 10.19 Independent Architecture Audit, Real RL/Guardrail Ablation Evidence, and a Proposed Architectural Comparison

A further, later stage of this same phase went back and audited the entire codebase's architecture from first principles, deliberately not leaning on Section 10.13's finding and instead re-deriving it independently. Its classification landed on "orchestrated modular pipeline with agent-like components." A pre-registered confirmatory equivalence test reports a primary 95% CI of **[-0.0818, 0.0021]** for the difference between PPO-plus-guardrails and a constant-action-plus-guardrails condition, against a pre-specified equivalence margin of **δ = 0.12**. (This test is cited from the project's existing confirmatory-experiment record, a two-way cluster bootstrap over 40 personas and 5 training seeds, and not reproduced here.) The interval sits entirely inside ±δ, which the pre-registered protocol reads as a genuine equivalence result, not merely a nonsignificant difference. This specific finding carries a disclosed caveat, and this report did not introduce either the caveat or its resolution. The project's own methodology audit (`research/audit/CODEX_HARNESS_AUDIT_BRIEF.md`, finding O7) flagged that a percentile CI built from only 5 seed clusters tends to run narrower than its nominal coverage. It called for a sensitivity recomputation before the equivalence classification could be treated as settled. That recomputation has in fact already been carried out and officially registered (`research/analysis/x3a_o7/O7_INTERPRETATION.md`, dated 2026-09-20, independent-reproduction gate R0: **PASS**). This corrects an earlier draft of this section, which wrongly described the recomputation as not yet performed. Under the pre-registered ±0.12 margin, all eight analyses in that registration classify as **"Equivalent,"** with no interval crossing the margin (the closest approach sits 0.0252 inside the lower bound). Those eight analyses are the primary registered estimate, a persona-only bootstrap, a conditional seed-level t-interval, and five leave-one-seed-out checks. Per that registration's own stated permissible wording: *"The registered X3-A classification (Equivalent, margin ±0.12) was unchanged under three pre-specified secondary sensitivity analyses (persona-only bootstrap, conditional seed-level t interval, leave-one-seed-out), on the five frozen checkpoints in simulation."* Superiority is explicitly not supported here: no interval's upper limit falls below -0.20. Equivalence within ±0.12 is not itself evidence of zero difference, either; one analysis variant's interval actually excludes zero on the PPO-favourable side. So the learned policy's own marginal contribution beyond the guardrail shield is reported as not statistically distinguishable from zero. The registered equivalence classification holds under this robustness check, on simulated personas only. No real-user claim is made.

**Real evaluator human-correlation evidence (replacing the Phase-2 abstract's unverifiable "93.3% baseline calibration" claim, Section 10.12 item 8).** Three raters independently scored 64 constructed candidate answers spanning 8 questions. The composite evaluator correlates with the human gold label at Spearman ρ = 0.3812 (95% CI [0.158, 0.577]). That is a moderate, exploratory result, reported here with its full uncertainty instead of some stronger but unverifiable historical figure, in keeping with this chapter's evidence discipline. An earlier draft of this section had wrongly stated that this evidence could not be located. In fact, the gold-label aggregation method and inter-rater reliability are documented in this project's canonical evidence record (`research/CANONICAL_SCIENTIFIC_TRUTH_CURRENT.md`). On aggregation: 54 of the 64 items used the mean of the three raters' scores. The remaining 10, where the three raters' scores spread by more than 0.20, were resolved by adjudication instead of averaging. On reliability: ICC(2,1) = 0.9528, ICC(2,k) = 0.9838, Krippendorff's α = 0.9523, all indicating a high level of agreement. That high reliability figure carries its own documented caveat. It is not a reason to discount it, but it is a reason not to over-read it either. The same source notes that category membership (the benchmark's 10 pre-defined answer-quality categories) explains roughly 98-99% of the variance between raters. So the reliability statistic mostly reflects how distinctly the benchmark's categories were constructed, not independent agreement on genuinely ambiguous cases. Separately, rater and adjudicator identities, qualifications, and any institutional review/consent process go undocumented in the repository. So, consistent with that gap, this report does not claim "independent experts" or "approved" review, and lists it again in Chapter 11, Section 11.4.

**A proposed, not-yet-executed architectural comparison.** This same later stage also produced a fully specified research design. Its purpose: formally comparing this specialised, orchestrator-coordinated architecture against a fair, equivalently-resourced unified single-controller baseline, using an equivalence contract, a 17-category benchmark, primary/secondary metrics, and a pre-specified statistical plan. None of it has been executed, though. No single-controller baseline has been built, and no comparative result of any kind exists at the time of writing. It is recorded here, and listed again in Chapter 11's future work, strictly as a design artifact, so it isn't mistaken for a completed experiment.

## 10.20 Final Correction Pass: Three Code-Submission Defects Found and Live-Docker-Verified Fixed, and Documentation Corrections

Going back through this report section by section and cross-checking every claim against the current source code, a final correction pass turned up two related defects in the code-submission scoring path (fixed, Table 10.2 items 4-5) along with a set of documentation-only inaccuracies, each corrected at its own location in the relevant chapters and summarised here for traceability. That wasn't the end of it, though — a subsequent, independent re-verification pass over this same section found that item 4's own fix description had actually understated how bad things were, implying the primary WebSocket scoring path was unaffected when it actually carried a separate, more severe defect of the same family (item 5 below). A third pass then tried to live-verify items 4 and 5 against a reachable Docker daemon, and in the process found and fixed a third defect (item 6) that the first two passes' fixes had been quietly depending on without realising it. All three defects are fixed now, and — unlike what the first two passes claimed — actually exercised against a live Docker sandbox rather than left sitting as "specified but unverified."

**Defect 1 (Table 10.2 item 4): `/api/run_code` always accepted code submissions regardless of correctness.** This REST endpoint is a secondary, quick-run code-execution path, distinct from the primary WebSocket `code_submission` flow covered as Defect 2 below. It looked up the active question's test cases via `getattr(sess, "_current_question", None)`. Since that attribute is never assigned anywhere on the session object, the lookup always returned `None`. That made `test_cases` always an empty list, which in turn made the endpoint's pass/fail check (`passed_count == total_tests`) vacuously true for zero executed tests. Every submission through this specific endpoint was reported as passing, regardless of whether the code was actually correct. The fix routes the endpoint through the orchestrator's existing `_get_current_question()` accessor. `agents/coding_executor/coding_executor.py`'s `is_accepted` check now also requires `total_tests > 0` before returning an "accepted" verdict, consistent with NFR-3's no-fabrication principle (Chapter 4, Section 4.3).

**Defect 2 (Table 10.2 item 5): the primary WebSocket `code_submission` handler trusted client-supplied scoring fields with no server-side re-execution.** This is the path that actually drives difficulty adaptation and session scoring for a candidate's coding answers, so the stakes here are higher. Unlike Defect 1, this handler did resolve the active question correctly via `_get_current_question()`, but only to look up metadata, not test cases. It never ran the sandbox itself. Instead it took `passed`, `tests_passed`, and `tests_total` straight from the client-sent WebSocket JSON payload (`apps/backend/main.py`, the `code_submission` branch). It fed them directly into `orchestrator.handle_code_submission()`, which uses them to compute the score and update session state. A client could send a WebSocket message claiming `tests_passed == tests_total` without the sandbox ever executing the submitted code. The system would accept it as genuine. That is an academic-integrity-relevant gap, not a cosmetic one. The fix has the handler resolve the active question's real test cases server-side (the same `_get_current_question()` accessor), and call the authoritative `evaluate_c_submission()` sandbox itself before scoring. `passed`/`tests_passed`/`tests_total` now come only from that server-side run; the client-sent values for these fields are no longer read at all.

**Defect 3 (Table 10.2 item 6): found only while attempting to live-verify Defects 1 and 2, not by reading the report or the code in isolation.** Driving a real Docker sandbox run against a real session surfaced the real problem. `apps/backend/main.py`'s production question-bank loader, `_load_question_bank_from_qns()`, never attached a `test_cases` field to the question objects it builds from `data/questions/qns.json`. It copies roughly fifteen other fields per question but silently drops this one. Had this gone unnoticed, Defects 1 and 2's fixes would have been *individually correct* (require `total_tests > 0`, never trust the client) but *jointly wrong in effect*. Every real question's `test_cases` would still resolve to an empty list, so `total_tests` would always be `0`. The new guard would then make every genuine code submission fail outright instead of being scored on its real correctness, swapping a false-accept defect for a false-reject one. A second, independent schema mismatch turned up at the same time. `qns.json`'s raw test-case fields (`input`/`expected_output`/`hidden`) don't match the field names `coding_executor.py` reads (`input`/`expected`/`is_hidden`/`is_mandatory`). So even a naive fix that copied `test_cases` through unchanged would have left every expected-output comparison matching against an empty string. The fix normalises each question's test cases into the sandbox's expected schema at load time and attaches them to the question dict.

**Verification status, stated plainly, for all three defects: this is now a live, Docker-verified result, not a specified-but-unverified one.** With a reachable Docker daemon available, a real session was created through the actual FastAPI app (`fastapi.testclient.TestClient`, not a mock). Its question queue was inspected for a genuine coding question (`C01`, 4 real test cases, 2 public + 2 hidden). The following was then run end-to-end against the live Docker C sandbox:
- **REST `/api/run_code`, known-correct code:** `3/4` tests passed, `coding_score: 0.75`, `status: wrong_answer`. This turned out to be a confirmed, precisely identified question-bank defect, upgraded from an earlier draft's vaguer "appears to have an inconsistent expected value." Question `C01`'s hidden test case 4 (`input: "5 8\n1 4 3 5 8"`) stores `expected_output: "1 2"`. Re-deriving it by hand against the array `[1,4,3,5,8]`, target `8`: only indices `(2,3)` actually sum to the target (`3+5=8`). The stored pair `(1,2)` sums to `4+3=7`, not `8`. The mathematically correct expected output is **`"2 3"`**, not the stored `"1 2"`. This is a confirmed error in `data/questions/qns.json`'s own data, not a defect in the evaluation code. It still means a genuinely correct candidate solution is denied full marks by this one hidden test case. It is left uncorrected in the dataset as part of this report (a question-bank content change, scoped outside this correction pass without separate authorisation). It is flagged here so it isn't mistaken for a code defect or silently worked around.
- **REST `/api/run_code`, known-incorrect code** (a stub that always returns `-1 -1`): `1/4` tests passed, `coding_score: 0.25`, correctly differing from the correct-code result.
- **WebSocket `code_submission`, the same incorrect code, submitted honestly (no forged fields):** `final_score: 0.25`, `tests_passed/tests_total: 1/4`, `passed: false`, `grade: F`. This is the real sandbox result, flowing through difficulty-adaptation scoring exactly as intended.
- **WebSocket `code_submission`, the same incorrect code, with a forged payload claiming `passed: true, tests_passed: 10, tests_total: 10`:** server response was identical to the honest case: `final_score: 0.25`, `tests_passed/tests_total: 1/4`, `passed: false`, `grade: F`. The forged fields were not read at all. This is the direct, live demonstration that Defect 2's trust-boundary gap is closed.
- **WebSocket `code_submission`, the same correct code, submitted honestly:** `final_score: 0.65`, `tests_passed/tests_total: 3/4`, consistent with the REST result. The score differs slightly from the raw `0.75` after the timing modifier, which is expected and separate from test-case scoring.
- The full Docker-dependent unit-test batch (`tests/unit/test_coding_executor.py`, `test_stage11_4_coding_verification.py`) was re-run too, with the daemon reachable: 47 passed. The one remaining failure is the same pre-existing, already-documented, deliberately-unaltered `obs[4]` issue (Section 10.11); zero newly-introduced failures. The non-Docker-dependent tests touching this code path (`test_orchestrator.py`, `test_timer_scoring.py`) were unaffected.

That closes the previously-open verification gap for all three defects. None of them is "specified but unverified" anymore. Each was exercised against real compiled-and-executed C code in the actual Docker sandbox, through the actual FastAPI application code, not a mock or a unit-level stub.
